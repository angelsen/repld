# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Research preview. The kernel, bridge, MCP protocol (exec / get_task / cancel), human gates, channel infrastructure, and the gist commands are live. When implementing, treat `docs/ARCHITECTURE.md` as the design spec (architecture, status checklist, design principles) and this file for subsystem details and invariants. README.md is user-facing only. Don't drift from the shape described here without discussion.

## Build & run

Python 3.12+, managed with **uv** using the `uv_build` backend (see `pyproject.toml`).

```bash
uv sync                                                                                         # install deps into .venv
uv run repld                                                                                    # runs the `repld:main` entrypoint
uv build                                                                                        # wheel + sdist via uv_build
uv run tests/smoketest.py --phase 12                                                            # end-to-end smoketest
ruff check --fix && ruff format && python3 scripts/align-comments.py --fix-all && basedpyright  # lint / format / align / type-check
make injected                                                                                   # regenerate src/repld/browser/injected_source.py
```

`scripts/align-comments.py --fix-all` runs last on purpose — it re-applies
column alignment to trailing `#` comments and `sig  → type` doc markers that
`ruff format` would otherwise collapse to a flat 2-space gap on every `.py`
file. This means a fresh `ruff format --check` run right after this command
reports drift again on those files — expected, not a bug; alignment is
deliberately the last word. Markdown is excluded from `ruff format`'s scope
entirely (`pyproject.toml`'s `extend-exclude`) for the same reason — ruff
0.16+ formats embedded Python code blocks in `.md` by default, which
collapsed the same alignment in README/docs/site examples.

`injected_source.py` is generated — never hand-edit it. `make injected` rebuilds
it from the pinned microsoft/playwright clone via `scripts/build_injected.py`
(node/esbuild needed at dev time only; the wheel ships the .py). Bumping the
engine means updating the clone, changing `PLAYWRIGHT_COMMIT` in the script,
rebuilding, and re-running the phase-6 browser tests.

No CI configured yet. If you add any, update this file.

## Releasing

Published to PyPI as `repld-tool`. Manual, no CI. The local `uv` is a wrapper
(`~/.local/bin/wrappers/uv`) that automates most of it — raw uv is `@ uv`.

```bash
# 1. Accrue changelog notes under CHANGELOG.md [Unreleased] as you work, and COMMIT them.
#    The bump needs a clean tree and promotes [Unreleased] → [X.Y.Z].
uv version --bump patch   # bumps pyproject + uv.lock, promotes changelog, commits "release repld-tool X.Y.Z", tags vX.Y.Z
rm -f dist/* && uv build  # clean stale artifacts first — publish refuses mixed versions
git push origin master --tags
uv publish                    # prints a review summary + a confirmation token (10-min TTL)
uv publish --confirm <token>  # GPG prompt for the PyPI token (from `pass pypi/uv-publish`), then uploads
```

Gotchas the wrapper enforces: clean working tree before `version --bump`; only
the target version in `dist/` before publish (it blocks on leftovers from a
prior release). Verify with the simple index (fast) — the JSON API lags:
`curl -s https://pypi.org/simple/repld-tool/ | grep X.Y.Z`. CHANGELOG covers
*packaged* changes only — `gists/` is not in the wheel. The docs site is a
separate pipeline nothing else prompts: if `site/src/content/docs/**` or
README changed since `gh-pages`' last deploy, finish the release with
`make deploy`.

## Key subsystems

All source lives under `src/repld/`. Individual files are self-describing; what matters is how they connect:

**Threading model:** The kernel runs the asyncio loop on a daemon thread (`run_forever`); the main thread runs the display consumer (or parks on a stop event in `--no-display` mode). IPC accept runs on its own thread, spawning per-connection reader threads that call into the dispatcher. This matters because user code in `exec` runs on the daemon thread's loop — blocking calls will stall the kernel.

**Nothing repld itself runs may block the shared loop.** The loop is the kernel: every cell, ticker and deferred task is on it, and a synchronous call inside an `async def` stalls all of them. Two places got this wrong, both in the browser observation pipeline, which runs on the loop once per tab *plus* once per iframe child around every mutation: `pre_observe` now reads its delta cutoff from `MAX(rowid) FROM events` rather than the `har_entries`/`console_entries` **views**, whose `MAX(id)` evaluated a whole CTE chain (22–82 ms) — the same cutoff, since both views derive `id` from `events.rowid` and rowids stay monotonic across the FIFO prune. `post_observe`'s `network_delta` genuinely needs the view, so it runs under `asyncio.to_thread` instead (`CDPSession.query` opens a per-call cursor precisely so another thread can read while the loop writes through the main connection); measured loop stall across the delta: 104 ms → 7 ms. The dashboard's Console/Network RPCs called the identical CTE chains synchronously on this same loop — a Refresh click stalled everything — and now go through `to_thread` too. The question for anything added to this pipeline, or to any coroutine the kernel runs, is not "is this fast" but "is this on the loop".

The deliberate counter-example: `CDPSession._async_prune` runs its FIFO delete *on* the loop on purpose — `create_task` gets it out of the recv handler only, but the SQL is a rowid-range op on a columnar store, ~7 ms flat at `MAX_EVENTS` regardless of row width and fired at most once per `PRUNE_CHECK_INTERVAL` events (under 10 µs amortised). Moving it would add a second writer to the event store for single-digit milliseconds saved. "Is this on the loop" is the question; "how long does it hold it" is the answer that decides.

A wedged loop is *reported*, not silently tolerated: a watchdog thread pushes `loop_blocked` past `REPLD_LOOP_BLOCK_THRESHOLD` (default 5 s) and cancels the longest-running non-internal task past `REPLD_LOOP_KILL_THRESHOLD` (default 30 s) — both printed in the boot banner (the journal, on a service-spawned kernel). Sub-second stalls like the prune's stay under it; the watchdog is a backstop for wedges, not a substitute for asking the question. `ipc.Server` accepts and reads on its own threads, so `repld status`/`log`/`gate` still answer a kernel whose loop is wedged — exactly when they're needed.

**Request flow:** Claude Code spawns `bridge.py` (stdio MCP). If a kernel for this project is already running, the bridge attaches to it immediately (`ipc.connect_to_kernel`) and every request forwards to it as below. If not, MCP discovery (`initialize`, `tools/list`, `resources/list`, static docs) is answered straight from `kernel.cache` (or a minimal static fallback if none exists yet) — no kernel spawns for that alone. The first request that actually needs live state (a real `tools/call`, a gist/browser `resources/read`) spawns a headless kernel via `spawn.py`, at which point the bridge proxies JSON-RPC over unix socket (`ipc.py`) → `protocol.py` dispatches to `exec`, `get_task`, `cancel`, or browser tools → `runtime.py` runs code in `__main__` → results (or `task_id` for deferred work) flow back. Channel notifications (`events.py`) flow kernel → bridge → Claude Code.

**State-file layering:** three modules, one job each, in dependency order. `paths.py` decides *where* state lives (cwd derivation, plus `--socket`/`REPLD_SOCKET` resolution). `state.py` decides *how* it's written and trusted (`atomic_write_json`, `open_private`, `read_lock`, `pid_alive`, `acquire_lock`, `sweep_dead_pid_files`) and imports nothing from repld. `ipc.py` is the socket layer only — `Session`, `Server`, `connect_to_kernel` (previously a grab-bag of five modules imported just to write a JSON file). `spawn.py` holds the one copy of the headless-kernel spawn, shared by `bridge.py` and `repld restart`, kept separate so the bridge (spawned every Claude Code session) doesn't have to import `lifecycle_cmd`.

- **Where the kernel lands is part of `spawn.py`'s job.** On systemd it goes to the user manager as a transient service (`repld-<slug>-<hash>.service`, keyed off the *resolved socket path* — not cwd, or two `--socket` overrides sharing a cwd collide on one unit name; the prefix is `paths.project_slug` for the default socket), because `start_new_session` alone detaches from the controlling terminal but neither reparents the process nor moves it out of the spawner's cgroup — a bridge-spawned kernel would otherwise be a child of that bridge, its state accounted to the terminal window. A service, never `--scope` (which keeps the parentage); journal output is the side benefit, since a bridge-spawned kernel has no terminal for `_report_boot_failure` to write to. Any systemd failure falls back to the plain `Popen` path. `REPLD_MEMORY_HIGH`/`REPLD_OOM_SCORE_ADJUST` are opt-in only — the kernel's OOM priority is unchanged by default.
- **Three more small modules, carved out for the same reason.** `channel.py` owns `push_channel`/`push_kind` — needs only `ipc` + `events`, so the six modules that push to channel (including the browser stack) import it at module level instead of function-locally importing `kernel`. `render.py` holds the ANSI palette and pure event formatters shared by the live TUI (`display.py`) and `repld log` (`log_cmd.py`), which must render the same events identically.
- **`bg.py` is `spawn(coro)` and nothing else.** asyncio keeps only a weak reference to a running task, so anything `create_task`'d and not held can be collected mid-flight — every fire-and-forget in the kernel is work whose loss reads as the browser having ignored you (a tab that attaches and records nothing, a `watch()` that skips a tab, a gate that renders no pill). `Fetch.requestPaused`'s handler is the sharp case: it's the only thing that ever resumes a paused request, so losing it hangs that request with `settle` waiting on it forever. It deliberately doesn't touch exceptions — the done-callback discards, so a raising task still surfaces the usual "never retrieved" warning.
- **Holding the task is only half of it — the dispatch has to be reachable.** `CDPSession._handle_event` stores the event *before* dispatching `Fetch.requestPaused`/`Runtime.bindingCalled`, under one `except Exception: logger.debug(...)` — a raise from the store must not skip both and recreate the exact hang `bg.spawn` exists to prevent. The store is guarded separately: everything after it is control flow, not recording.
- **Pass `loop=` from sync callers that aren't on the loop themselves (`Tab`'s property setters) — and that path must never call `loop.create_task`.** From a foreign thread, `create_task` queues the task's first step without the `_write_to_self()` that `call_soon_threadsafe` does, so an idle loop is never woken and the coroutine simply doesn't run — it can look like it's working only because the watchdog probes once a second and drains the queue on every wakeup. `spawn()` hops to the loop with `call_soon_threadsafe` and creates the task there (returning None, since the handle doesn't exist yet on the caller's thread) — not `run_coroutine_threadsafe`, which gives the task no name, and an unnamed loop task is exactly what `kernel._pick_victim` treats as fair game when the watchdog escalates.

**Builtins injected into `__main__`:** The kernel injects these names at startup — they are the user/agent-facing API surface: `notify(content, **meta)`, `defer(coro, label)`, `every(seconds, delay=0)` (decorator), `ask(prompt)`, `confirm(prompt)`, `choose(prompt, options)`, `no_display(value)`, `browser` (lazy descriptor, only when `repld[browser]` is installed). Plus `help` — a `pydoc.Helper` bound to `sys.stdout` rather than the stdlib builtin, because pydoc's default pager forks `less(1)` on the kernel tty, which bypasses the `_Tee` and deadlocks the loop.

**Doc system (`help.py`):** Agent-facing docs are split across non-overlapping surfaces. Keep them in sync:
1. **INSTRUCTIONS** (dynamic) — behavioral model composed at MCP init by `build_instructions()`. Includes exec model always; browser model only when `browser` exists in `__main__`; gist signatures extracted via AST from available gists. This is what the agent reasons with. Terse; always loaded.
2. **Tool descriptions** — per-tool what + gotchas, defined in `protocol.py`.
3. **Topics** — pure API reference for `repld help <topic>`, defined as `_TOPICS` in `help.py`. The one exception is `migration`, which is explanatory rather than API: it answers why a project has no `.pyrepl.*`, `.mcp.json` or `repl.py`, which is a question about *absence* and so has no surface to document. It belongs here rather than in `repld://docs/*` because a doc resource is permanent surface advertised every session, and this expires — delete it once 0.1.x is not a version anyone upgrades from. `_reference()`, the always-loaded pointer block, derives its topic list from `_TOPICS` for that reason: adding or removing one must not leave a hand-written list behind.
4. **MCP resources** — on-demand docs read via `repld://docs/*`, each a standalone constant in `help.py`: `GUIDE` (`docs/guide`, execution model + gist patterns + conventions), `BROWSER_GUIDE` (`docs/browser`, full browser API reference), `PLAYBOOK` (`docs/playbook`, workflow-building methodology), `PRODUCTION` (`docs/production`, graduating a gist's core logic out of repld into FastMCP/FastAPI/etc). Registered in `protocol.py`'s resource list; read on demand rather than always loaded.

**Browser (`browser/`):** the package layout, consumer-first, is `pool.py` (`BrowserPool` over N Chrome instances, plus the `LazyBrowser` descriptor) → `browser.py` (`Browser`, one instance) → `session.py` (the WebSocket and sessionId multiplexing) → `cdp.py` (`CDPSession`, per-target DuckDB) → `tab.py` (the JS/DOM facade, with `tab_query.py`'s query surface). `target.py` is the leaf everything can import: the short-target-ID vocabulary (`make_target` and friends), `TabNotFoundError`, and the two things both facades need above them. `__init__.py` is re-exports only. **Monkeypatching note:** `BrowserPool` resolves `Browser` through `pool.py`'s namespace, not the package re-export — a test patching `repld.browser.Browser` silently leaves the real class in play. 24 MCP tools registered dynamically by `protocol.py` only when `browser` exists in `__main__` (i.e. `repld[browser]` is installed). See `docs/browser.md` for full design rationale.

- **Selector resolution is engine-only.** `selector.py` translates repld's grammar to Playwright selector strings; `inject.py` resolves them through a vendored build of Playwright's `InjectedScript` (`injected_source.py`, generated by `make injected` — never hand-edit), instantiated lazily once per document per session, in an isolated utility world with a main-world tier when `Page.createIsolatedWorld` is refused, and a loud `EngineUnavailable` when both fail — there is no legacy first-visible-pick fallback. The strictness policy: visibility ranks, never filters — a lone hidden match is still the target; only multiple matches with no single visible winner error, with a candidate digest. Two engine spellings are load-bearing: `internal:text`/`internal:label`, because the public `text=` engine parses the `"…"s` exact suffix as literal text and there is no public `label` engine. `Runtime.executionContextsCleared` and stale-context call errors drop the cached handle (retry-once, the `Tab._exec` shape); aria-refs live inside the engine instance, so every drop kills them — the error tells the caller to take a fresh `browser_tree` snapshot.
- **Fetch interception is enabled on `get()`/`open()` tabs; `watch()` tabs attach lightweight**, with on-demand body access via `Network.getResponseBody`. Interception registers on `*` but capture does not — `capture._should_capture_body` is what separates them, since `Fetch.enable` takes no resource-type filter and every paused response reaches Python regardless. Capturing costs a round trip plus ~2.7× the resource's bytes (`Fetch.getResponseBody` consumes the internal buffer, so a captured response replays via `fulfillRequest` rather than continuing) — worth it for JSON/XHR/document traffic, not assets, which are skipped via `har_entries`' own `is_asset` derivation so capture and query agree on what `tab.network()` hides by default. `fetch_body` falls back to `Network.getResponseBody` for anything with no stored body, so skipping loses nothing.
- **`since=` on the four query methods is epoch seconds — one base, three source clocks.** `har_summary.last_activity` is already epoch seconds (from `requestWillBeSent.wallTime`); `Runtime.Timestamp` behind `console()` is epoch *milliseconds*; `Network.MonotonicTime` behind `sse()`/`lifecycle()` counts from an arbitrary origin and must be offset against a request carrying both. `tab_query` converts all three to the epoch-seconds base before comparing — comparing a caller's `since=` against the raw column instead (as `console()` once did) silently matches every row. `time.time()` is the base because it's the only clock a caller can produce without a prior query.
- **Settle counts a per-session `_inflight` map via `CDPSession.inflight_count()`, never `len()`.** A request enters on `requestWillBeSent`, leaves on `loadingFinished`/`loadingFailed` — which a `text/event-stream` response never emits until the stream closes, so a live SSE connection must not pin the tab at its full settle deadline. Streamed responses instead leave `_inflight` when their headers land (network went quiet there; only the body is open-ended); `_INFLIGHT_MAX_AGE` ages out anything still open after 60s as a backstop, and `reattach_session` clears the map outright.
- **`_sessions` and `_browsers` are loop-owned state; almost every reader runs off-loop.** The loop mutates both on every tab attach/detach/`Target.targetDestroyed`, while the *sync* half of the browser API runs on whatever thread called it (`browser_dispatch` on the IPC reader thread; `runtime._eval` puts every sync exec cell in `asyncio.to_thread`). Those methods snapshot with `list(...)` before walking — atomic under the GIL — or a popup opening mid-call raises "dictionary changed size during iteration". Running *on* the loop is not on its own license to skip the snapshot: the real question is whether the loop body can *yield* — an `await` inside a walk hands control to another task that mutates the same dict, and resuming raises the identical error (`_rpc_browser_connect`/`_rpc_browser_disconnect` are `async def` on this loop, so a dashboard Connect click can land mid-`watch()` fan-out). Snapshot whenever the body can yield or the method may run off-loop; the two exemptions are a loop body that never awaits, and one that returns on first match without resuming iteration (`BrowserPool.open`/`fetch`). Snapshotting fixes the crash, not the semantics — a browser connecting mid-fan-out just misses that sweep, accepted rather than held under a cross-request lock. `BrowserPool.disconnect` removes the snapshotted keys individually rather than `clear()`, or a `connect()` landing mid-sweep gets dropped from the registry with a live WebSocket nothing would close. `BrowserSession.find_by_target_id` / `BrowserPool.resolve_tab` carry the same rule reached from a sync method reached via `asyncio.to_thread`.
- **The DuckDB close is loop-owned state too, and snapshotting can't help it.** `CDPSession.cleanup()` runs on the loop while `query`/`query_dicts`/`clear_events`/`fetch_body` take per-call cursors so they can run off it — a `Target.targetDestroyed` landing mid-query must not close the connection under a live cursor. `_db_lock` spans cursor-acquisition-through-close on the read side and the close on the other, so `cleanup()` waits out an in-flight read (bounded by the slowest CTE) rather than racing it.
- **Writing loop-owned state off-thread needs its own path.** `browser_tabs`/`browser_clear` route through `_run_sync_on_loop` so `clear_events`'s resets of `_event_count`/`_inflight` land where `settle` reads them — but the tool isn't the only caller: `browser.clear()` in a sync exec cell and the dashboard's `tab.clear()` both reach it via `asyncio.to_thread`, racing `store_event`'s `self._event_count += 1` on the loop (a read-modify-write a `= 0` can land inside and lose). `clear_events` splits itself: the `DELETE` stays off-loop (per-call cursor, by design); the counter reset goes through `call_soon_threadsafe` unless the caller is already on the loop. A missed reset drifts the count *low*, never high, and `_async_prune`'s next `SELECT COUNT(*)` self-corrects. When a sync method touches loop-owned state, ask which callers reach it, not which tool does.
- **Pin/gate bridge:** `tab.pin(reason)` injects a floating pill via `Runtime.evaluate` + `beforeunload` guard; `tab.confirm()`/`tab.choose()` route human gates to the pill UI; button clicks flow back via `Runtime.bindingCalled` → `resolve_gate()`. That binding is session-scoped — Chrome removes `window.__repld_resolve` from the page when the adding session detaches — so `_reattach_core` re-adds it (alongside the Fetch restore) whenever `_binding_handler` is set; without that, a reconnect leaves the pill's buttons calling an undefined function. `Page.addScriptToEvaluateOnNewDocument` (the label bar) is session-scoped the same way, and hides worse: the bar is live DOM, so it survives the current document and only fails to come back on the *next* navigation — precisely what the registration is for. **The rule to carry forward: anything registered per-session — `addBinding`, `addScriptToEvaluateOnNewDocument`, `Fetch.enable` — belongs in `_reattach_core`, not at its call sites.** The injected-engine handle is the same rule as cache rather than registration: its objectId dies with the sessionId, so `inject.invalidate(cdp)` lives in `_reattach_core` too — nothing to replay, the next selector call re-instantiates.
- **The two injection routes in `pin.py` differ on `document.body`.** `_PIN_JS` goes in via `Runtime.evaluate` on a live page, so it dereferences `document.body` freely. `_LABEL_JS` is an `addScriptToEvaluateOnNewDocument` registration that runs at document *start*, before the parser has built `<body>` — reaching through `document.body` at top level throws and takes out the whole mount, on exactly the path meant to survive a navigation. `runImmediately: True` masks this during manual testing, since it also evaluates against the currently-loaded document where body exists. Anything registered this way defers to `DOMContentLoaded` when `document.body` is null.

**Dashboard (`dashboard.py`, `dashboard_html.py`):** pure-stdlib async HTTP server on an ephemeral port — an inline HTML control panel (GET /) and a JSON-RPC API (POST /api) exposing kernel state: pid, uptime, active tasks, tickers, connected browser tabs. The markup is the second module and nothing else — `PAGE`/`UNAUTHORIZED_PAGE`, 657 lines of HTML/CSS/JS that were half of `dashboard.py`. A Python module rather than package data so it still ships in the wheel with no `pyproject.toml` entry; `PAGE`'s `__DASHBOARD_TOKEN__` placeholder is substituted at serve time by the same handler that refuses to serve it unauthenticated. Port, API token, and browser restore state live in the hint file (`kernel.dashboard`); `save_hint()` runs as soon as the server binds and again on every browser state change, and **merges** into the existing file, rewriting the browser keys only when `browser.peek()` returns a pool — the startup call doesn't have one, and blanking `chrome_ports`/`patterns` at boot would throw away the previous kernel's restorable session before `_restore_browser_state` reads it.

**`GET /` is authenticated, because it carries the token** — serving it to anyone who asks would hand the credential to every process on the box (loopback is not a uid boundary; `sessions` names every project cwd and the browser RPCs reach the user's Chrome). It accepts `?token=` or a `repld_token_<port>` cookie (set on the way in so a refresh survives the page dropping the query via `replaceState`; per-port because cookies ignore the port and sibling dashboards would otherwise clobber one another's). `POST /api` stays **Bearer-only** — a cookie rides along on requests the user didn't initiate, so it must never be sufficient by itself. The sidebar's links to sibling dashboards carry each peer's token via `_sessions_with_tokens()`, kept in `dashboard.py` rather than `sessions.register` since a token belongs to a dashboard and `repld status`/`stop --all` have no business carrying credentials.

**Gist system (`gists.py`, `gist_api.py`, `gist_deps.py`, `gist_links.py`):** custom import hook (`_GistFinder` + `_GistImportHook`) wraps `builtins.__import__`, tracks mtimes, evicts stale modules from `sys.modules` on re-import. Module docstring first line → auto-injected into MCP instructions (override with `__repld_help__ = "..."`); constructor signatures are extracted via AST and shown alongside it.

- **MCP tools.** Gists register typed `_tool_*` functions — `scan_tools()` discovers them across all gist files and infers each schema from the signature plus the docstring's first line (`Annotated[T, "..."]` supplies a parameter description); `resolve_tool(name)` imports the owning gist and returns its `_tool_{name}` handler. The pre-0.1.0 `__repld_tools__` list is removed and ignored; `gist_lint`'s `legacy` rule is the only thing that still reports one.
- **Dependencies.** `__repld_deps__ = ["httpx>=0.27"]` — `gist_deps.scan_deps()` AST-scans at boot, `gist_deps.install_deps()` prompts interactively and installs via `uv pip install --target` into a shared, interpreter-versioned directory (`~/.local/share/repld/deps/py3.12`), never the active venv: a project venv gets pruned by `uv sync`, and a bound kernel's prefix is an ephemeral `uv run` overlay that differs per invocation. Versioned because compiled wheels are built for one minor version; `ensure_deps_on_path()` *appends* the directory, so the project's own packages always shadow a gist dep. Every import is recorded in a central registry (`~/.config/repld/gist-registry.json`, name → path/project/last_used).
- **Cross-project links (`gist_links.py`).** `repld gist add <name>` resolves a registered gist's path, AST-follows its same-dir sibling imports, and records absolute paths in a committed `./gists/.links` manifest — without copying. At boot `_load_links()` populates the `_linked` name→path overlay, consulted by `_GistFinder`/`_iter_gist_files` *after* local dirs so local gists always shadow; stale entries are skipped, never auto-rewritten. `repld gist list` shows local + linked (flagging stale); `rm <name>` / `rm --stale` unlink.
- **`repld gist fetch <gist-url>` is `new`'s sibling, not `add`'s** — it *copies* a GitHub gist's `.py` files into `./gists` (or `~/.repld/gists` under `--global`) with a `# source:` header, so nothing tracks it afterwards and `rm` (unlink-only) can't undo it. It enforces the same three collision scopes as `add_link` (local, global, already-linked) — including the third, which `add_link` itself was missing: the manifest is a flat name→path map, so a co-linked sibling could silently repoint a name another linked gist depends on. It deliberately does *not* install the fetched file's `__repld_deps__` the way `add` does — `add` links code you wrote elsewhere; this is code from a URL, whose dependency list shouldn't drive an install before the file has been read. It accepts a bare gist id, a `gist.github.com` URL, or a raw `gist.githubusercontent.com` one (`_GIST_HOSTS`) and refuses everything else, since the file lands somewhere a kernel imports at boot.
- **The three modules share helpers via an intentional call-time-attribute import cycle** (`gists._parse`, `gists.registry`, `gist_links._linked`, ...). `gist_api.py` sits underneath that cycle rather than inside it: the AST-in, API-text-out half — `_parse` and the `_format_*` renderers behind `repld://gists/{name}`, the MCP instructions, and `repld gist list` — touching none of `gists.py`'s mutable hook state, so it imports nothing from repld and can be imported outright. `gists` re-exports `_parse`/`_dunder_value` for `gist_links`/`gist_deps`/`gist_lint` to reach as `gists._parse`. Same monkeypatching rule as the browser split: a test patching `gist_api._parse` patches the definition, but `gists` resolves it through its own namespace — `phase_3_patch_targets` catches the mismatch.

## Architecture (target shape)

Eleven CLI subcommands, all dispatched from `repld:main`:

- `repld` — long-running Python kernel for the cwd, with the live TUI display. Takes the project's flock mutex (`kernel.flock`) and writes `kernel.lock` with `{pid, socket_path, cwd, started_at, dashboard_port}`; listens on a unix-domain socket. Losing the flock is not an error — it prints a note and exits 0 so the incumbent is adopted, never raced. No flags select a project bootstrap: a `repld_init.py` in the cwd is auto-detected (see the invariant below).
- `repld bridge` — stdio MCP subprocess Claude Code spawns for a registered repld server. Inherits cwd, attaches to a kernel that's already running or lazily spawns one on first real use, proxies stdio MCP ↔ the kernel's IPC socket, and relays channel notifications (`notifications/claude/channel`) back to the client. See the slim-loader invariants below. `repld bridge --ephemeral` inverts both halves for a private, single-use kernel: it spawns eagerly (before the first message, not on first real tool call) at a private socket path outside `PROJECTS_DIR`, and kills it (SIGTERM, SIGKILL after `WAIT_STEPS`) plus reclaims its whole directory the moment stdin closes, instead of leaving it running for the next session to attach to. Still `spawn.spawn_headless` underneath, spawned with `cwd=os.getcwd()` regardless of the socket override — so `./gists`, `repld_init.py`, `.env`, and `.venv` binding all resolve exactly as they do for the persistent kernel; only the state addressing is one-off. Mutually exclusive with `--socket`, enforced for free: skipping `resolve_socket_path` for this branch means a stray `--socket` just falls through to `check_args` as an unrecognised flag.
- `repld log` / `status` / `stop` / `restart` / `dashboard` — observe and control a kernel this terminal never started (`log_cmd.py`, `lifecycle_cmd.py`, `dashboard_cmd.py`).
- `repld gate` — list pending human gates, `repld gate answer <id> <value>` resolves one (`gate_cmd.py`). The headless kernel's answering surface; see the gate invariant below. Shares `exec_cmd`'s `_connect`/`_call` rather than keeping a second copy of the IPC handshake. **It is the one subcommand whose argv has a region no flag parser may enter:** an `ask` answer is free text, and all three parsers that run here reach across the whole list by design — `paths.resolve_socket_path` consumes `--socket PATH` from anywhere, `--json` was filtered the same way, and `cli_args.wants_help` scans every argument on purpose (that is what makes `gist rm foo --help` ask for usage). So `repld gate answer <id> deploy --socket now` answered `"deploy now"` and silently repointed the connection at a kernel called `now`. `_split_answer` cuts argv at `answer <gate_id>` before any of them run; everything past that is the answer verbatim, and flags for the command go *before* the verb. The `[--socket PATH]` the usage used to show trailing `<value>` is gone with it — it was never distinguishable from an answer that says the same words.
- `repld help [TOPIC]` — agent-facing docs. Single source of truth shared with the MCP `initialize` `instructions` field (composed by `src/repld/help.py:build_instructions()`). Never let the two drift.
- `repld exec [CODE]` — human-facing CLI. With no args, interactive REPL over IPC (shared namespace). With a string arg, one-shot execution. Same kernel, same state as the agent.
- `repld gist` — command group: `new <name>` (scaffold `./gists/<name>.py`), `fetch <gist-url>` (download a GitHub gist's `.py` files into `./gists`, or `~/.repld/gists` with `--global`), `add <name>` (link a registered gist from another project), `rm <name>` / `rm --stale` (unlink), `list` (local + linked + linkable-from-registry), `lint [--local] [name...]` (AST checks — docstring first line, return-shape docs, undeclared `__repld_deps__`, legacy tool API; `gist_lint.py`, suppress with `# gistlint: ignore=<rule>`). Lint's default scope is everything a kernel here would import — global + local + linked, including private (`_`-prefixed) files, which are importable and can carry real dep/shape problems despite never being exposed as gists. `--local` narrows to `./gists` (so the exit code gates one project) and resolves names against that directory first rather than through `_find_gist`'s kernel precedence (global before local), or a global gist sharing a stem makes `lint --local <name>` reject a file the no-argument form lints happily. Lint is read-only, so it calls `gists.install(..., create=False)` — name resolution only, not the boot-time side effect of creating both gist directories. Unknown verbs error (no verb-less scaffold alias); every verb rejects flags/positionals it doesn't understand via `cli_args.check_args`. Top-level CLI dispatch is a single `_SUBCOMMANDS` table in `cli.py` driving both dispatch and `--help`.
- **Subcommand argument validation lives once, in `cli_args.py`.** `check_args(prog, argv, usage, flags=, positionals=)` refuses unrecognised flags and surplus positionals; `wants_help` scans *every* argument for `-h`/`--help`, not just the first, so `gist rm foo --help` asks for usage instead of unlinking foo. Separate from `cli.py`, which routes *between* subcommands rather than validating within one. Every subcommand goes through it now — `stop`, `restart`, `status`, `dashboard`, `gate`, `help`, `gist_cmd`, and `repld bridge` (which previously validated nothing, so `--help` started a proxy that blocks on stdin forever). A verb whose flags take a value calls `check_args` *after* consuming them — `fetch` strips `--name NAME` first, the same ordering every client subcommand uses for `--socket` — and passes no `flags=`, since by then anything still starting with `-` is unknown by construction. `check_args` rejects only *surplus* positionals, so a verb that requires one still needs its own `if not argv` after the call, as `add` has always had. `log_cmd` deliberately stays out: `-n N` takes a value, so its argv needs a real parser loop rather than a flag-set membership test.
- `repld browser [ARGS...]` — re-exec `repld ARGS...` under `uv run` with the `browser` and `http` extras (`duckdb` + `websockets` + `pillow`; all three are required, and all three are imported eagerly — `browser/png.py` pulls in PIL at module scope for `Tab.screenshot`'s resize, so installing only the first two leaves `kernel._inject_builtins` swallowing a `ModuleNotFoundError` and reporting the extra as absent), so browser features work without adding `repld-tool` to the project's dependencies. `http` (`httpx`) rides along so `tab.http_client()` is available the moment `browser.acquire()`/`get()` is, without a second install. Preserves a local editable checkout (detected via `direct_url.json` distribution metadata) instead of silently falling back to the published package, so dev changes are picked up (`src/repld/relaunch.py`).

Key invariants to preserve when building this out:

- **One process, one asyncio loop.** The kernel owns a single shared loop so `asyncio.create_task(...)` from any exec call survives past the exec return and can push to channel on completion.
- **A lock taken across a CDP command must have an unlocked core, because the command can re-enter it.** `BrowserSession.execute` reconnects and retries on a dead socket, and `_reconnect` → `_reattach_core` re-enables the session's domains and its Fetch capture — on the *same task* that issued the command. So any `async with self._lock:` wrapped around an `execute` is reachable from inside itself, and `asyncio.Lock` is not reentrant: it deadlocks outright, with no traceback and no timeout, on a loop that is the whole kernel. Both locks on that path are split the same way — `reattach_session` wraps `_reattach_core`, `enable_fetch` wraps `_enable_fetch_core` — and the reconnect path always calls the core. Phase 6 asserts the non-deadlock directly; the control in that test confirms the wrapper version hangs.
- **`exec` returns fast or defers, and which one it did is decided once.** If user code finishes within `timeout` (default 2s) return inline; otherwise return `{task_id, done: false}` and push a channel notification on completion. The two are settled by `tasks.mark_nudged`, which takes the promise of a push under `_tasks_lock` and refuses it if the cell already finished — including inside the window `_exec`'s own `snapshot()` opens, which re-reads the entire spill file. It returns whether it got the promise, and `_exec` answers with the result when it didn't; `claim_done_push` is the paired read on the finalize side. Deciding these separately meant a cell landing in that window got neither: no push, and a reply saying one was coming. Every cell with output spills to `$XDG_RUNTIME_DIR/repld/{pid}-{tid}.out` from byte 1; the inline response carries a head+tail preview and the absolute spill path. Agents use the standard Read/Grep tools on that path — there is no `read_spill` MCP tool.
- **Stdlib only in core.** Zero required runtime dependencies. Optional extras (`repld[pretty]` for rich-rendered display, `repld[http]` for `tab.http_client()`) gate anything heavier. Don't pull new deps into the base package. The bar for a new extra is kernel coupling, not reuse frequency: `http_client` is a neutral primitive six gists had already reinvented. A URL-pattern readiness cache proposed alongside it stayed a gist instead — it bakes in policy (auto-applying a cached per-site heuristic), which "resist adding per-service helpers" argues against regardless of how many gists would use it.
- **Per-cwd, localhost-only — and localhost is not a uid boundary.** The IPC socket stays on `127.0.0.1` or a user-only unix socket. This is a dev-time tool; never add anything that would make it safe to expose. Loopback keeps other *hosts* out, not other *users*: the unix socket is uid-protected by its mode, but the dashboard's TCP port is reachable by anything running on the box, which is why its token gates `GET /` and not just `POST /api`. Every file backing this data is 0600 for the same reason. When adding a surface here, the question is which of the two protections it actually has.
- **Runtime state lives under XDG, never in the project.** `paths.py` is the single source of truth — including the two gist directories (`global_gists_dir()`/`local_gists_dir()`/`gist_dirs()`, the last being the kernel's own import precedence, previously derived by hand at fourteen sites across `gist_cmd`, `gists`, `gist_links` and `kernel`): `$XDG_RUNTIME_DIR/repld/projects/{basename}-{sha256(realpath)[:8]}/`, created 0700. Every file is the socket path with a different suffix (`kernel.sock` → `.lock`/`.flock`/`.dashboard`/`.events`/`.cache`), so `--socket`/`REPLD_SOCKET` moves the whole set coherently. `kernel.cache` (`paths.cache_for`) holds the last-computed `initialize`/`tools/list`/`resources/list` triple, written once at boot and deliberately never cleaned up — it's what lets the *next* bridge answer MCP discovery before a kernel exists. Per-process scratch is the one exception: task spills, resource spills, and browser screenshots belong to the process, not a project, and sit directly in `RUNTIME_DIR`, named `{pid}-…` so a booting kernel can reclaim a dead pid's leftovers in one pass (`state.sweep_dead_pid_files`) — keep the prefix on anything new written there.
  **Two rules, both needed.** The boot sweep only ever collects *dead* pids, no help to a process designed to stay up for weeks, so a live kernel ages out its own: task spills by registry entry (`tasks._prune_spill_files`, `_EVICT_AGE`), and everything with no registry entry — oversized tool responses, screenshots — by mtime (`state.sweep_own_stale_files` via `tasks._sweep_orphans`). Anything new that writes here goes through the task registry or inherits the orphan sweep; don't add a third scheme, and don't reintroduce a project-directory fallback.
- **Nothing under `RUNTIME_DIR` is readable by other users.** Without `XDG_RUNTIME_DIR` the root falls back to `/tmp/repld-{uid}` — uid-suffixed so it can't be pre-created and owned by someone else. `paths.ensure_runtime_dir()` is the only thing that creates that root; call it before writing anywhere beneath. `kernel._claim_project` calls it first, because `state.acquire_lock`'s own `mkdir(parents=True, mode=0o700)` applies the mode only to the leaf — a root brought into being as an implicit parent (e.g. via `--socket`/`REPLD_SOCKET` pointing under it before anything ensured it) comes out 0755 at umask default, skipping the foreign-owner refusal. Every state file is created 0600 up front (`state.open_private`, or `atomic_write_json(chmod=0o600)`) — never `open()` then chmod, which leaves a window at 0644.
- **One kernel per project, enforced by flock.** `kernel.flock` is opened `O_CREAT` *without* `O_TRUNC` and never replaced — `kernel.lock` is rewritten atomically via `os.replace`, which would move the inode out from under a flock held on it. That's why they're two files.
- **The kernel binds itself to the project's interpreter; it is never spliced across versions.** `bind.py` is the single answer to "which Python should we be". Installed as a uv tool, repld's console script pins its own interpreter via the shebang, so a kernel would otherwise be unable to import the project it sits in. Entry points that run or create a kernel (`repld`, `bridge`, `restart`) call `bind.rebind_exec()` first, which re-execs through `uv run --with-editable`/`--with` under the project venv's Python; `exec` is deliberately excluded — it only resolves a lock path and talks IPC, and the code it runs executes inside the kernel, which is already bound. `REPLD_BOUND` is the sentinel that stops `uv run … repld bridge` re-entering forever, and `is_bound()` is the semantic check (is the venv's site-packages on `sys.path`?) rather than a prefix comparison, because under a uv overlay `sys.prefix` is a cache directory. **Only a version-matched venv may be `addsitedir`'d onto a running kernel** (`bind.adopt`) — a venv's compiled extensions are built for one minor version while its pure-Python and `abi3` packages import anywhere, so splicing a mismatched one half-works, and a partial success is worse to debug than the clean refusal plus the enriched `ModuleNotFoundError` that `gists._explain_missing` raises instead. `project_venv()` prefers `./.venv` over `$VIRTUAL_ENV`: cwd identifies a project everywhere else in repld, and an ambient `$VIRTUAL_ENV` belongs to whatever shell launched the client, not necessarily to this project.
- **A few tools are served by the bridge, and the split is narrow on purpose.** `bridge_tools.py` holds them; a tool belongs there *only* if it must work while the kernel is dead or if it kills the kernel (`repld_restart` is both). Everything else goes in `protocol.py`, or the bridge accretes into a second, worse kernel. The wiring is deliberately one-directional: the kernel advertises `bridge_tools.SCHEMAS` from `_tools_list`, and the bridge intercepts the matching `tools/call` on the *request* side, before the liveness ladder. It never rewrites a response — see the byte-pipe note below. `protocol._tools_call` carries a matching branch that errors by name, since a bridge tool arriving at the kernel means the client connected to the socket directly.
- **Anything both sides of the socket answer lives in `core_schemas.py`.** The bridge answers `initialize`/`tools/list`/`resources/list` itself whenever no kernel has ever run in the project, so every one of those responses has two authors, and a constant declared in only one is silently wrong for exactly the cold-start sessions nobody is watching. `CORE_TOOLS`, `DOC_RESOURCES`, `DOC_HELP_ATTRS`, `REGISTRY_RESOURCE`, `STATIC_RESOURCES`, `RESOURCE_TEMPLATES`, `CAPABILITIES`, `PROTOCOL_VERSION`, `SUPPORTED_VERSIONS`, `negotiate_version`, and the `response`/`error`/`notification` envelope builders all live here for that reason — the bridge can't import `protocol.py`, so the module stays pure stdlib data. `STATIC_RESOURCES` is `DOC_RESOURCES` plus `REGISTRY_RESOURCE`, kept out of `DOC_RESOURCES` because that list also drives `DOC_HELP_ATTRS` and the registry has no `help.py` attribute behind it. `initialize` actually has *three* authors — `repld exec` handshakes over the socket too — which is why `PROTOCOL_VERSION` lives here rather than as a hand-synced copy in `protocol.py`.
  **Version negotiation is echo-what-they-asked-for:** `negotiate_version` returns a requested version we support verbatim, our latest otherwise (never an unknown string), and both `initialize` authors call it — the bridge deliberately does not read the cached kernel answer here, since that was negotiated with a different session's client. 2025-06-18 is the deliberate ceiling (everything repld uses from it — tool annotations, `structuredContent`/`outputSchema`, resource templates — is additive, so one code path can serve older revisions too); 2026-07-28 removes the `initialize` handshake outright and is a bridge rearchitecture, not a bump. `get_task`'s declared `outputSchema` commits `_get_task` to a conforming `structuredContent` on every success — a field added to `tasks.snapshot()` must be added to the schema too.
  `CAPABILITIES` matters most: both parties may only use what was negotiated at `initialize`, so a drifted copy *disables* a feature rather than degrading it (`listChanged` is what lets the bridge invalidate the client's tool list after respawning a kernel). `build_discovery_cache()` deliberately excludes it, so a warm `kernel.cache` can't paper over a drift either — phases 3 and 15 assert both paths negotiate exactly `core_schemas.CAPABILITIES`. The `instructions` field carries the same two-author problem in prose: `static_instructions()` is `build_instructions()` minus what needs a live kernel (browser model, gist listing, registered gist tools), composed from the same constants in the same order — a cold session must be told `./gists` exists too, and nothing re-sends `instructions` after the lazy spawn.
- **The bridge is a stateful proxy, not a byte-pipe.** It must never close its own stdout (MCP client dispatchers are single-shot and cannot re-handshake), must cache the client's `initialize` and replay it onto every fresh kernel (a respawned kernel is uninitialized and would queue channel pushes forever), must answer orphaned in-flight ids with `-31001`, and must probe liveness *before* forwarding rather than retrying after a failure — `exec` runs arbitrary code and must never run twice. Diagnostics go to stderr only.
- **Kernel spawn is lazy, but only when there's genuinely nothing to attach to.** `Bridge._handle_client_line` first tries a cheap, no-spawn connect (`_try_attach_existing`) — if a kernel for this project is already running (the common case: a second window, a kernel a prior session left up), it attaches for free and every request forwards live, exactly as before. Only when that fails does MCP discovery fall back to `kernel.cache` (`_try_bridge_intercept`), and only a real `tools/call` or gist/browser `resources/read` triggers `_ensure_kernel`'s actual spawn-and-wait. That last part is enforced by `_NEEDS_KERNEL`, not by exhaustion: anything the intercept declines that isn't one of those two is answered `-32601` by the bridge, and an unparseable line is dropped. Both used to fall through to the spawn, so a client-side `ping` or one truncated stdin line paid the full 5 s spawn-and-wait for a method no kernel of ours implements. `notifications/initialized` is tracked (`_client_initialized`) rather than always replayed on first spawn — replaying it early, before the client genuinely sent it, would let a channel push escape the kernel's pre-init queue ahead of schedule. `--ephemeral` is the one deliberate exception to "lazy": its whole premise is a kernel for exactly this session, so `run()` calls `_ensure_kernel()` before reading stdin at all — which also means `initialize` itself forwards to a live kernel instead of `_try_bridge_intercept`'s cache/static answer, since that path is only taken while `self._sock is None`.
- **The project bootstrap is a file, not a flag.** `kernel.INIT_FILENAME` (`repld_init.py`) is auto-detected in the kernel's cwd and executed into `__main__` at boot — the same shape as `_load_dotenv()` reading `./.env` and `gists.install()` putting `./gists` on `sys.path`: the project directory is the source of truth. (It was `--init FILE` until 0.2, which only fired for a hand-started kernel that won the flock — the bridge's lazy spawn, `repld restart`, and `repld_restart` all silently dropped it, on precisely the projects that are useless without it.) Two ordering rules: it runs **after** `_start_services` binds the socket, since the bridge only waits `WAIT_STEPS × WAIT_STEP_SECONDS` (5s) for a spawn to become connectable and a bootstrap that raises a tunnel takes longer; and `_run_init_file` must **never raise**, including on the file read, since a failed bootstrap needs a live kernel to be fixed from. `./.env` is read once at boot too, and unlike `./gists` does not reload on mtime — `load_dotenv` is public (`from repld import load_dotenv`) and never overrides an existing var, so a name captured while empty must be cleared before reloading. It pushes `init_loaded` on success (the only signal a bridge-spawned kernel came up pre-populated) and `init_error` on failure.
  **`_run_cell` waits on `_init_done` before running any cell**, so the first `exec` after a lazy spawn can't race the bootstrap and find a bare `__main__`; the flag is set unconditionally after `_run_init_file` returns, since a kernel nobody can run code in cannot be repaired regardless of how the bootstrap went. The bootstrap cell itself passes `wait_ready=False`, or it would wait on its own completion. **`exec` is not the only lazy-spawn trigger, so it is not the only waiter** — `_NEEDS_KERNEL` also spawns on a gist or browser `tools/call`, which answer inline or not at all, so `protocol._tools_call` blocks on `_Context.wait_ready()` before dispatching either (on the IPC thread, not the loop — which is why `exec` must not come through it: `_run_cell`'s await is what turns a slow bootstrap into an ordinary completion push instead). Both waits are bounded by the one `_INIT_WAIT_SECONDS`, the same budget `_run_init_file` gives the bootstrap, so no waiter can outlive what it waits for.
- **A human gate must stay answerable on a kernel with no pane.** `ask`/`confirm`/`choose` park a cell until `gates.resolve_gate` is called, by exactly three callers: the TUI's stdin reader, a pinned tab's pill, and `repld gate answer` (via the kernel-side `gates/list`/`gates/resolve` JSON-RPC methods in `protocol.py`). Only the third exists on an auto-spawned kernel (`--no-display`, stdin on `/dev/null` — the common case since lazy spawn), so anything adding a gate surface must keep that route working. They race, first-wins; `resolve_gate` returns whether *this* caller answered. Coercion lives once in `gates.parse_response`, so a pane and the CLI can't disagree about what `y` or `2` means.
  The two *boot* prompts (restoring a browser session, installing gist deps) ask before the loop/display/tee exist, so they go through `gates.tty_prompt` rather than a gate, sharing `gates.yes_by_default` (`_YES` plus the empty-string `[Y/n]` default) — each previously kept its own looser `in ("", "y", "yes")`, so `1`/`true` declined the browser-restore prompt while confirming a `confirm()`. **The pane's claim on stdin releases when its reader ends, not just when it starts** — `_stdin_owned` left true after an EOF on a redirected stdin used to make `tty_prompt` decline for the rest of the process's life.
  `gates/list`/`gates/resolve` are deliberately JSON-RPC methods, not MCP tools: an agent able to answer its own `confirm()` defeats the primitive. When `gates._has_terminal` is false and no pill is in play, the `awaiting_human` push carries the literal `repld gate answer` command. "No pill in play" is about `kind`, not just pinnedness — the pill is buttons with no text input, so `_show_gate` renders `confirm`/`choose` but draws nothing for an `ask`; deciding on pinnedness alone left `tab.ask()` with no surface at all.
  **A gate that ends without an answer is announced, not just forgotten.** `timeout=` expiring and the awaiting cell being cancelled both close a gate with `resolve_gate` never called, so `_gate`'s `finally` emits `HumanPromptClosed(gate_id, reason)` alongside popping it — `gates._gates` is what `open_gates` reads, so `repld gate` self-corrects, but a surface keeping its own mirror (`display._open_gates`) only learns from the event; without it, `_stdin_reader_loop` (which routes to the *newest* open gate) went dead, silently resolving a gate the kernel had already dropped. `_Gate.answered`, not an inspection of the future, is what tells the two endings apart — a cancelled future is indistinguishable from one whose `set_result` lost a race — and `resolve_gate` claims it *before* `set_result`, releasing it again on `InvalidStateError`.
- **The pane's stdin has exactly one reader, so `tty_prompt` is boot-only.** `gates.tty_prompt` is the synchronous sibling of the gate primitives, talking straight to the controlling terminal for the two things that must ask before the loop/display/tee exist (installing gist deps, restoring a browser session). Past boot it must not run: `display._stdin_reader_loop` is parked in `readline()` on the same `sys.__stdin__` and consumes every line regardless of an open gate, so a second reader blocks behind its buffer lock while discarding the answer — reachable via `gist_deps.install_deps` from `gists._check_reload`/`_scan_new_deps`, i.e. from `builtins.__import__` inside a user cell, which on an `await` cell is the shared loop: the watchdog's cancel then has no await point to land on, and the kernel wedges until a human types something. `gates._stdin_owned` (set by `run_display`, distinct from `_has_terminal`, set at the top of `_boot_runtime`) makes `tty_prompt` return `None` past that point — `_has_terminal` alone is already true during the boot prompt, so gating on it would kill the one call meant to work. Anything new that reads stdin directly asks `stdin_owned()` first.
- **Targeted push for call-scoped output, broadcast for ambient.** A task carries the `ipc.Session` that started it (`task["origin"]`); `_maybe_push_done` routes its completion there. `@every` errors, console errors, browser connect/disconnect, and bare `notify()` stay broadcast; if the origin disconnected, drop the push rather than falling back to broadcast (`events.emit(ChannelPush(...))` fires either way, so `repld log` still sees it).
  **Which of the two a piece of output is gets decided by `tasks._current_task`, and anything that outlives a cell has to say so.** `_task_scope` binds it, wrapping `_run_cell` and `_run_deferred` — both of which end, so inheriting via `copy_context()` is correct for a `create_task`/`defer()` from a cell body. A `@every` ticker goes through neither and outlives the cell by weeks, so inheriting silently made it call-scoped forever: every downstream cap keys on that id and clears only on the owning cell's `CellDone` (`display._truncated_tasks`, `eventlog._chunk_capped`), so the ticker filled a *finished* cell's 4 KB budget and was then dropped by the pane and the event log — the only surfaces a headless kernel has — until `_prune_spill_files` unlinked the file an hour on and the writes went nowhere. `_start_ticker` clears it (`tasks.set_current_task(None)`) so ticks render unattributed and uncapped, like the boot banner. The rule: if it can still be running after the cell that created it returned, it is ambient and must clear the id rather than inherit one.

## Design principles (from README)

- **Substrate, not library.** Expose small composable primitives (`notify`, `defer`, `@every`, `browser.watch`, `browser.get`) and let the LLM write integration code against live pages/APIs/DBs. Resist adding per-service helpers. Before calling a new primitive done, check that its output plugs straight into the others — a ref usable by `click`/`type` directly, not descriptive text the agent has to hand-translate into a selector first.
- **Channel push over polling.** Long jobs, file watchers, webhooks, and timers all surface as `<channel>` injections rather than requiring the agent to poll.
- **Shared `__main__` namespace.** Human and agent operate on the same module dict — don't sandbox the agent into an isolated scope.
