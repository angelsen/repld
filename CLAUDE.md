# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Research preview. The kernel, bridge, MCP protocol (exec / get_task / cancel), human gates, channel infrastructure, and the gist commands are live. When implementing, treat `docs/ARCHITECTURE.md` as the design spec (architecture, status checklist, design principles) and this file for subsystem details and invariants. README.md is user-facing only. Don't drift from the shape described here without discussion.

## Build & run

Python 3.12+, managed with **uv** using the `uv_build` backend (see `pyproject.toml`).

```bash
uv sync                                 # install deps into .venv
uv run repld                            # runs the `repld:main` entrypoint
uv build                                # wheel + sdist via uv_build
uv run tests/smoketest.py --phase 12          # end-to-end smoketest
ruff check --fix && ruff format && basedpyright   # lint / format / type-check
make injected                                 # regenerate src/repld/browser/injected_source.py
```

`injected_source.py` is generated — never hand-edit it. `make injected` rebuilds
it from the pinned microsoft/playwright clone via `scripts/build_injected.py`
(node/esbuild needed at dev time only; the wheel ships the .py). Bumping the
engine means updating the clone, changing `PLAYWRIGHT_COMMIT` in the script,
rebuilding, and re-running the phase-6 browser tests.

No CI configured yet. If you add any, update this file.

## Releasing

Published to PyPI as `repld-tool`. Manual, no CI. The local `uv` is a wrapper
(`~/.local/bin/wrappers/uv`) that automates most of it — raw uv is `@ uv`.

```bash
# 1. Accrue changelog notes under CHANGELOG.md [Unreleased] as you work, and COMMIT them.
#    The bump needs a clean tree and promotes [Unreleased] → [X.Y.Z].
uv version --bump patch        # bumps pyproject + uv.lock, promotes changelog, commits "release repld-tool X.Y.Z", tags vX.Y.Z
rm -f dist/* && uv build       # clean stale artifacts first — publish refuses mixed versions
git push origin master --tags
uv publish                     # prints a review summary + a confirmation token (10-min TTL)
uv publish --confirm <token>   # GPG prompt for the PyPI token (from `pass pypi/uv-publish`), then uploads
```

Gotchas the wrapper enforces: clean working tree before `version --bump`; only
the target version in `dist/` before publish (it blocks on leftovers from a
prior release). Verify with the simple index (fast) — the JSON API lags:
`curl -s https://pypi.org/simple/repld-tool/ | grep X.Y.Z`. CHANGELOG covers
*packaged* changes only — `gists/` is not in the wheel. The docs site is a
separate pipeline nothing else prompts: if `site/src/content/docs/**` or
README changed since `gh-pages`' last deploy, finish the release with
`make deploy`.

`tests/smoketest.py` is the entire test suite — no pytest setup. It starts a real kernel + bridge subprocess and drives MCP JSON-RPC over stdio. `--phase N` runs phases 1..N (default 3, current ceiling 17). When you add a feature, extend a phase rather than introducing a separate harness. Each phase lives in its own file under `tests/phases/` (e.g. `core.py`, `channels.py`, `defer.py`).

## Key subsystems

All source lives under `src/repld/`. Individual files are self-describing; what matters is how they connect:

**Threading model:** The kernel runs the asyncio loop on a daemon thread (`run_forever`); the main thread runs the display consumer (or parks on a stop event in `--no-display` mode). IPC accept runs on its own thread, spawning per-connection reader threads that call into the dispatcher. This matters because user code in `exec` runs on the daemon thread's loop — blocking calls will stall the kernel.

**Nothing repld itself runs may block the shared loop.** The loop is the kernel: every cell, ticker and deferred task is on it, and a synchronous call inside an `async def` stalls all of them. Two places got this wrong and both were in the browser observation pipeline, which runs on the loop once per tab *plus* once per iframe child around every mutation. `pre_observe` read its delta cutoff from the `har_entries` / `console_entries` **views**, whose `MAX(id)` evaluates a whole CTE chain (22–82 ms) — it reads `MAX(rowid) FROM events` now, which is the same cutoff because both views derive `id` from `events.rowid` and rowids stay monotonic across the FIFO prune. `post_observe`'s `network_delta` genuinely needs the view, so it runs under `asyncio.to_thread` instead; `CDPSession.query` opens a per-call cursor precisely so another thread can read while the loop writes through the main connection. Measured loop stall across the delta: 104 ms → 7 ms. The dashboard was the third: its Console and Network RPCs are `async def` on this same loop and called `tab.console()` / `tab.network()` — the identical CTE chains — synchronously, so a Refresh click stalled everything. They go through `to_thread` now too. When adding anything to that pipeline, or to any coroutine the kernel runs, the question is not "is this fast" but "is this on the loop". The counter-example worth knowing, because it looks like a fourth instance and isn't: `CDPSession._async_prune` runs its FIFO delete *on* the loop, and should stay there — `create_task` gets it out of the recv handler only, but the SQL is a rowid-range op on a columnar store, measured at ~7 ms flat at `MAX_EVENTS` regardless of row width and fired at most once per `PRUNE_CHECK_INTERVAL` events. That is under 10 µs amortised, at the level the observation pipeline was optimised *down* to, and moving it would add a second writer to the event store (own cursor, plus an in-flight guard against concurrent deletes) for single-digit milliseconds. "Is this on the loop" is the question; "how long does it hold it" is the answer that decides. A wedged loop is *reported*, not silently tolerated: a watchdog thread pushes `loop_blocked` past `REPLD_LOOP_BLOCK_THRESHOLD` (default 5 s) and cancels the longest-running non-internal task past `REPLD_LOOP_KILL_THRESHOLD` (default 30 s) — both are printed in the boot banner, which on a service-spawned kernel means the journal rather than a terminal. Sub-second stalls like the prune's stay under it, so the watchdog is a backstop for wedges, not a substitute for asking the question. Note what *isn't* on it — `ipc.Server` accepts and reads on its own threads, so `repld status` / `log` / `gate` still answer a kernel whose loop is wedged, which is exactly when you need them.

**Request flow:** Claude Code spawns `bridge.py` (stdio MCP). If a kernel for this project is already running, the bridge attaches to it immediately (`ipc.connect_to_kernel`) and every request forwards to it as below. If not, MCP discovery (`initialize`, `tools/list`, `resources/list`, static docs) is answered straight from `kernel.cache` (or a minimal static fallback if none exists yet) — no kernel spawns for that alone. The first request that actually needs live state (a real `tools/call`, a gist/browser `resources/read`) spawns a headless kernel via `spawn.py`, at which point the bridge proxies JSON-RPC over unix socket (`ipc.py`) → `protocol.py` dispatches to `exec`, `get_task`, `cancel`, or browser tools → `runtime.py` runs code in `__main__` → results (or `task_id` for deferred work) flow back. Channel notifications (`events.py`) flow kernel → bridge → Claude Code.

**State-file layering:** three modules, one job each, in dependency order. `paths.py` decides *where* state lives (derivation from cwd, plus `--socket`/`REPLD_SOCKET` resolution). `state.py` decides *how* it's written and trusted (`atomic_write_json`, `open_private`, `read_lock`, `pid_alive`, `acquire_lock`, `sweep_dead_pid_files`) and imports nothing from repld. `ipc.py` is the socket layer only — `Session`, `Server`, `connect_to_kernel`. Keep it that way: `ipc.py` was previously a grab-bag five modules imported just to write a JSON file. `spawn.py` holds the one copy of the headless-kernel spawn, shared by `bridge.py` and `repld restart`; it's a separate module so the bridge (spawned every Claude Code session) doesn't have to import `lifecycle_cmd`. **Where the kernel lands is part of that job:** on systemd it goes to the user manager as a transient service (`repld-<slug>-<hash>.service`, keyed off the *resolved socket path* like every other per-project file — not cwd, or two `--socket` overrides sharing a cwd would collide on one unit name; the prefix is the socket's parent directory basename, i.e. `paths.project_slug` for the default socket), because `start_new_session` alone detaches from the controlling terminal but neither reparents the process nor moves it out of the spawner's cgroup — so a bridge-spawned kernel used to be a child of that bridge, with its multi-gigabyte state accounted to the terminal window. A service, never `--scope`: `--scope` runs in the caller's own context and would keep the parentage. Journal output is the side benefit that matters, since a bridge-spawned kernel has no terminal for `_report_boot_failure` to write to. Any systemd failure falls back to the plain `Popen` path — spawning must never become less reliable than it was. `REPLD_MEMORY_HIGH` and `REPLD_OOM_SCORE_ADJUST` are opt-in only; both override deliberate policy, and the kernel's OOM priority is unchanged by default. Three more modules exist for the same reason — small, widely-depended-on, and cheaper than the thing they were carved out of. `channel.py` owns `push_channel` / `push_kind`: it needs only `ipc` + `events`, so the six modules that push to channel (including the browser stack) import it at module level instead of function-locally importing `kernel`. `render.py` holds the ANSI palette and the pure event formatters shared by the live TUI (`display.py`) and `repld log` (`log_cmd.py`) — the two surfaces render the same events and are meant to look identical, so the strings live in one place. `bg.py` is `spawn(coro)` and nothing else: **asyncio keeps only a weak reference to a running task, so anything `create_task`'d and not held can be collected mid-flight.** Every fire-and-forget in the kernel is work whose loss reads as the browser having ignored you — a tab that attaches and records nothing (`_enable_domains`), a `watch()` that skips a tab (`_auto_attach`), a gate that renders no pill — and the `Fetch.requestPaused` handler is the sharp one, since it is the only thing that ever resumes a paused request and losing it hangs that request in Chrome with `settle` waiting on it. It deliberately doesn't touch exceptions: the done-callback discards and nothing more, so a raising task still surfaces the usual "never retrieved" warning. **Holding the task is only half of it — the dispatch has to be reachable.** `CDPSession._handle_event` stored the event *before* dispatching `Fetch.requestPaused` and `Runtime.bindingCalled`, under one `except Exception: logger.debug(...)`, so a raise from the store skipped both and re-created the exact hang `bg.spawn` exists to prevent — without needing a GC. The store is guarded separately now: everything after it is control flow rather than recording, and losing an event is a gap in history where losing the resume wedges the tab. Pass `loop=` from the sync callers that aren't on the loop themselves (`Tab`'s property setters) — **and that path may not call `loop.create_task`**, which is the mistake it shipped with. From a foreign thread `create_task` queues the task's first `__step` without the `_write_to_self()` that `call_soon_threadsafe` does, so the loop is never woken and on an idle one the coroutine simply does not run; it read as working only because the loop watchdog probes once a second and every wakeup drains the queue, i.e. each off-loop `tab.label = …` was riding an unrelated thread's timer for its liveness. Under `PYTHONASYNCIODEBUG=1` `_check_thread` raises instead. `spawn` hops to the loop with `call_soon_threadsafe` and creates the task there, returning None because the handle doesn't exist yet on the caller's thread. Not `run_coroutine_threadsafe`, which would otherwise be the obvious answer: it gives the task no name, and an unnamed loop task is precisely what `kernel._pick_victim` treats as fair game when the watchdog escalates — so going through it would hand the watchdog our own fire-and-forget work as the thing to cancel.

**Builtins injected into `__main__`:** The kernel injects these names at startup — they are the user/agent-facing API surface: `notify(content, **meta)`, `defer(coro, label)`, `every(seconds, delay=0)` (decorator), `ask(prompt)`, `confirm(prompt)`, `choose(prompt, options)`, `no_display(value)`, `browser` (lazy descriptor, only when `repld[browser]` is installed). Plus `help` — a `pydoc.Helper` bound to `sys.stdout` rather than the stdlib builtin, because pydoc's default pager forks `less(1)` on the kernel tty, which bypasses the `_Tee` and deadlocks the loop.

**Doc system (`help.py`):** Agent-facing docs are split across non-overlapping surfaces. Keep them in sync:
1. **INSTRUCTIONS** (dynamic) — behavioral model composed at MCP init by `build_instructions()`. Includes exec model always; browser model only when `browser` exists in `__main__`; gist signatures extracted via AST from available gists. This is what the agent reasons with. Terse; always loaded.
2. **Tool descriptions** — per-tool what + gotchas, defined in `protocol.py`.
3. **Topics** — pure API reference for `repld help <topic>`, defined as `_TOPICS` in `help.py`. The one exception is `migration`, which is explanatory rather than API: it answers why a project has no `.pyrepl.*`, `.mcp.json` or `repl.py`, which is a question about *absence* and so has no surface to document. It belongs here rather than in `repld://docs/*` because a doc resource is permanent surface advertised every session, and this expires — delete it once 0.1.x is not a version anyone upgrades from. `_reference()`, the always-loaded pointer block, derives its topic list from `_TOPICS` for that reason: adding or removing one must not leave a hand-written list behind.
4. **MCP resources** — on-demand docs read via `repld://docs/*`, each a standalone constant in `help.py`: `GUIDE` (`docs/guide`, execution model + gist patterns + conventions), `BROWSER_GUIDE` (`docs/browser`, full browser API reference), `PLAYBOOK` (`docs/playbook`, workflow-building methodology), `PRODUCTION` (`docs/production`, graduating a gist's core logic out of repld into FastMCP/FastAPI/etc). Registered in `protocol.py`'s resource list; read on demand rather than always loaded.

**Browser (`browser/`):** the package layout, consumer-first, is `pool.py` (`BrowserPool` over N Chrome instances, plus the `LazyBrowser` descriptor) → `browser.py` (`Browser`, one instance) → `session.py` (the WebSocket and sessionId multiplexing) → `cdp.py` (`CDPSession`, per-target DuckDB) → `tab.py` (the JS/DOM facade, with `tab_query.py`'s query surface). `target.py` is the leaf everything can import: the short-target-ID vocabulary (`make_target` and friends), `TabNotFoundError`, and the two things both facades need above them now that they are separate modules. `__init__.py` is re-exports and nothing else — it held all three facade classes inline until they were carved out, the one module that hadn't had `tab.py`'s treatment. **Note what that means for monkeypatching:** `BrowserPool` resolves `Browser` through `pool.py`'s namespace, not the package re-export, and a test patching `repld.browser.Browser` silently leaves the real class in play. 24 MCP tools registered dynamically by `protocol.py` only when `browser` exists in `__main__` (i.e. `repld[browser]` extra is installed). **Selector resolution is engine-only: `selector.py` translates repld's grammar to Playwright selector strings, `inject.py` resolves them through a vendored build of Playwright's `InjectedScript` (`injected_source.py`, generated by `make injected` — never hand-edit), instantiated lazily once per document per session, in an isolated utility world with a main-world tier when `Page.createIsolatedWorld` is refused, and a loud `EngineUnavailable` when both fail — there is no legacy first-visible-pick path to fall back to.** The strictness policy honors the old ranking invariant (visibility ranks, never filters: a lone hidden match is still the target; only multiple matches with no single visible winner error, with a candidate digest), and two engine spellings are load-bearing: `internal:text`/`internal:label`, because the public `text=` engine parses the `"…"s` exact suffix as literal text and there is no public `label` engine at all. `Runtime.executionContextsCleared` and stale-context call errors drop the cached handle (retry-once, the `Tab._exec` shape); aria-refs live inside the engine instance, so every drop kills them — the error says to take a fresh `browser_tree` snapshot. CDP integration via WebSocket multiplexer. DuckDB event store for network/console queries (HAR-style). Fetch domain interception for proactive body capture is enabled on `get()`/`open()` tabs; `watch()` tabs attach lightweight with on-demand body access via `Network.getResponseBody`. **Interception registers on `*` but capture does not, and `capture._should_capture_body` is the only thing that separates them** — `Fetch.enable` takes no resource-type filter, so every paused response reaches Python and the predicate decides. Capturing is not free: `Fetch.getResponseBody` consumes the internal buffer, so a captured response has to be replayed with `fulfillRequest` rather than continued, which is a round trip plus ~2.7× the resource's bytes on the debug socket. Worth it for the JSON/XHR/document traffic the store exists to make greppable; not for assets, which it skips using `har_entries`' own `is_asset` derivation — the same five resource types and mime markers, deliberately, so capture and query agree about which rows `tab.network()` hides by default. Nothing is lost by skipping: `fetch_body` falls back to `Network.getResponseBody` for anything with no stored body. Observation pipeline (`observe.py`) returns accessibility tree + network delta + console delta after mutations, once `settle` sees the network go quiet. **`since=` on the four query methods is epoch seconds — one base, three source clocks.** `har_summary.last_activity` is already epoch seconds (derived from `requestWillBeSent.wallTime`), `Runtime.Timestamp` behind `console()` is epoch *milliseconds*, and `Network.MonotonicTime` behind `sse()` and `lifecycle()` counts from an arbitrary origin and has to be offset against a request carrying both. Each method compared the caller's number against its raw column until `tab_query` converted, so only `network()` behaved as documented — `console(since=time.time())` matched every row, the exact opposite of the request. `time.time()` is the base because it is the only one a caller can produce without first making a query; row_id is cheaper and is what `pre_observe` cuts on internally, but it is not reachable from outside. Settle counts a per-session `_inflight` map through `CDPSession.inflight_count()`, never `len()`: a request enters on `requestWillBeSent` and leaves on `loadingFinished`/`loadingFailed`, which a `text/event-stream` response never emits until the stream closes — so a single SSE connection used to pin that tab at its full deadline for the rest of the session. Streamed responses leave when their headers land (for settle's purposes the network went quiet there; only the body is open-ended), and `_INFLIGHT_MAX_AGE` ages out anything still open after 60 s, far enough above settle's own 5 s that it can only evict something genuinely stuck. `reattach_session` clears the map outright for the same reason. **`_sessions` and `_browsers` belong to the loop, and almost everything that reads them doesn't run there.** The loop mutates both on every tab that opens or closes (attach, detach, `Target.targetDestroyed`), while the *sync* half of the browser API runs on whatever thread called it — `browser_dispatch` answers some tools on the IPC reader thread, and `runtime._eval` puts every pure-sync exec cell in `asyncio.to_thread`, so `browser.tabs` typed into a cell is already off-loop. Those methods therefore snapshot with `list(...)` before walking (atomic under the GIL); without it a popup opening mid-call raises "dictionary changed size during iteration", attributable to the user's browsing rather than to anything repld did. Running on the loop is **not** on its own a licence to skip the snapshot, and reading it that way is what left `BrowserPool`'s async fan-out unguarded for five releases. The question is whether the loop body can *yield*: an `await` inside `for b in self._browsers.values()` hands control back, another task runs `connect()` or `disconnect()`, and resuming raises the identical error — reachable in practice, since `_rpc_browser_connect`/`_rpc_browser_disconnect` are `async def` on this same loop, so a dashboard Connect click lands mid-`watch()` fan-out. So the rule is: snapshot when the body can yield, or when the method may run off-loop. The two genuine exemptions are an async loop whose body never awaits, and one that `return`s out on the first match without ever resuming iteration (`BrowserPool.open`/`fetch`). Note snapshotting fixes the crash, not the semantics — a browser connected midway through a fan-out just misses that sweep, which is accepted rather than held under a lock across N round trips. `BrowserPool.disconnect` needs one thing more: it removes the snapshotted keys individually instead of `clear()`, or a `connect()` landing mid-sweep gets dropped from the registry with a live WebSocket nothing would ever close. `BrowserSession.find_by_target_id` is the same rule reached from the other direction: it never awaits, but `BrowserPool.resolve_tab` is a plain sync method on the injected `browser` object, so `browser.resolve_tab(...)` in a pure-sync cell runs it in `asyncio.to_thread` — `resolve_tab` snapshotted `_browsers` and then walked `_sessions` live. **The DuckDB close is loop-owned state too, and snapshotting cannot help it:** `CDPSession.cleanup()` runs on the loop while `query`/`query_dicts`/`clear_events`/`fetch_body` take per-call cursors precisely so they can run off it, so a `Target.targetDestroyed` landing mid-query closed the connection under a live cursor. `_db_lock` spans cursor-acquisition-through-close on the read side and the close on the other, which means `cleanup()` waits out an in-flight read — bounded by the slowest CTE, and deliberate, since the alternative is the crash. *Writing* loop-owned state off-thread is the harder case and isn't fixed by snapshotting: `browser_tabs` and `browser_clear` go through `_run_sync_on_loop` so `clear_events`' resets of `_event_count` / `_inflight` land where `settle` reads them. **Routing at the tool boundary was only half of it, though, because the tool is not the only caller** — `browser.clear()` typed into a pure-sync exec cell runs in `asyncio.to_thread`, and the dashboard reaches `tab.clear()` the same way, so both still wrote those fields from a foreign thread and raced `store_event`'s `self._event_count += 1` on the loop, which is a read-modify-write a `= 0` can land inside and lose. `clear_events` therefore splits itself: the `DELETE` stays where it is (per-call cursor, off-loop by design) and the counters go through `call_soon_threadsafe` unless the caller is already on the loop. The scheduled reset can miss events arriving in the gap, so the count drifts *low*, never high, and `_async_prune` recounts with `SELECT COUNT(*)` on its next sweep — bounded and self-correcting, which a lost increment is not. When a sync method touches loop-owned state, ask which callers reach it, not which tool does. The DuckDB query methods are the deliberate exception in the other direction — per-call cursor, off-loop on purpose. Pin/gate bridge: `tab.pin(reason)` injects a floating pill via `Runtime.evaluate` + `beforeunload` guard; `tab.confirm()`/`tab.choose()` route human gates to the pill UI; button clicks flow back via `Runtime.bindingCalled` → `resolve_gate()`. **That binding is session-scoped, so it has to be re-registered on every reattach** — Chrome removes `window.__repld_resolve` from the page when the session that added it detaches, and `Tab._setup_binding` only ever runs on the first pin (or on the heartbeat's `'reload'` branch, which a navigation-triggered reattach reaches and a WebSocket reconnect does not). `_reattach_core` re-adds it whenever `_binding_handler` is set, next to the Fetch restore it already did; without that, a reconnect left the pill looking live with buttons that called an undefined function *after* clearing the gate from their own queue. **The label registration is the same rule and outlived that fix**: `Page.addScriptToEvaluateOnNewDocument` is session-scoped too, and its restore lived only in `Tab._reattach` — the navigation path — so a WebSocket reconnect dropped it. That one hides better than the binding did, because the failure is *delayed*: the bar is live DOM, so it survives on the current document and only fails to come back on the next navigation, which is precisely what the registration is for. `_reattach_core` owns both now, and `Tab._reattach` owns neither. **The rule to carry forward: anything registered per-session — `addBinding`, `addScriptToEvaluateOnNewDocument`, `Fetch.enable` — belongs in `_reattach_core`, not at its call sites.** The injected-engine handle is the same rule as *cache* rather than registration: its objectId dies with the sessionId, so `inject.invalidate(cdp)` lives in `_reattach_core` too — nothing to replay, the next selector call re-instantiates. Terminal and browser resolve the same Future — first wins. **The two injection routes in `pin.py` are not interchangeable, and the difference is `document.body`.** `_PIN_JS` goes in through `Runtime.evaluate` on a live page, so it dereferences `document.body` freely. `_LABEL_JS` is a `Page.addScriptToEvaluateOnNewDocument` registration, which runs at document *start* — before the page's own scripts and before the parser has built `<body>` — so reaching through `document.body` at top level throws and takes out the whole mount. That is what it did, on exactly the path the registration exists for: surviving a navigation. It looked fine because `runImmediately: True` *also* evaluates the script against the currently-loaded document, where body does exist, so setting a label worked and the bar then silently failed to come back. Anything new registered that way defers to `DOMContentLoaded` when `document.body` is null. See `docs/browser.md` for full design rationale.

**Dashboard (`dashboard.py`, `dashboard_html.py`):** Pure-stdlib async HTTP server on an ephemeral port. Serves an inline HTML control panel (GET /) and a JSON-RPC API (POST /api) exposing kernel state: pid, uptime, active tasks, tickers, connected browser tabs. The markup is the second module and nothing else — `PAGE` and `UNAUTHORIZED_PAGE`, 657 lines of HTML/CSS/JS that were half of `dashboard.py` and the half a reader of the server had to scroll past. A Python module rather than package data so it still ships in the wheel with no `pyproject.toml` entry; `PAGE`'s `__DASHBOARD_TOKEN__` placeholder is substituted at serve time, by the same handler that refuses to serve it unauthenticated. Port written to the hint file (`kernel.dashboard` in the project's runtime dir), which also carries the API token and the browser restore state. `save_hint()` runs as soon as the server binds — `repld status` reads the token from it, and a restart reads the port back to reclaim it — and again on every browser state change. It **merges** into the existing file and only rewrites the browser keys when `browser.peek()` returns a pool: every browser-initiated call has one, the startup call doesn't, and blanking `chrome_ports`/`patterns` at boot would throw away the previous kernel's restorable session before `_restore_browser_state` reads it. **`GET /` is authenticated, because it carries the token.** The page needs the token inlined to call `POST /api`, so serving it to anyone who asks handed the credential to every process on the box — loopback is not a uid boundary, and `sessions` names every project cwd while the browser RPCs reach the user's Chrome. It accepts `?token=` (what `repld dashboard` opens with, read from the 0600 hint file) or a `repld_token_<port>` cookie, set on the way in so a refresh survives the page dropping the query from the address bar via `replaceState`. The cookie name is per-port because cookies ignore the port and sibling dashboards would otherwise clobber one another's. `POST /api` stays **Bearer-only** — a cookie rides along on requests the user didn't initiate, so it must never be sufficient by itself. The sidebar's links to sibling dashboards carry each peer's token, which `_sessions_with_tokens()` reads from that project's hint file; it lives in `dashboard.py` rather than `sessions.register` because a token belongs to a dashboard, and `repld status` / `stop --all` read the same registry with no business carrying credentials.

**Gist system (`gists.py`, `gist_api.py`, `gist_deps.py`, `gist_links.py`):** Custom import hook (`_GistFinder` + `_GistImportHook`) wraps `builtins.__import__`, tracks mtimes, evicts stale modules from `sys.modules` on re-import. Module docstring first line → auto-injected into MCP instructions. Override with `__repld_help__ = "..."`. Constructor signatures extracted via AST and shown alongside the description. Gists register MCP tools with typed `_tool_*` functions — `scan_tools()` discovers them across all gist files and infers each schema from the signature plus the docstring's first line (`Annotated[T, "..."]` supplies a parameter description); `resolve_tool(name)` imports the owning gist and returns its `_tool_{name}` handler, called with keyword arguments. The pre-0.1.0 `__repld_tools__` list was removed in 0.2 and is ignored; `gist_lint`'s `legacy` rule is the only thing that reports one. Tools appear in `tools/list` automatically alongside built-in tools. Gists declare external dependencies via `__repld_deps__ = ["httpx>=0.27"]` — `gist_deps.scan_deps()` AST-scans at boot, `gist_deps.install_deps()` prompts interactively and installs via `uv pip install --target` into a shared, interpreter-versioned directory (`~/.local/share/repld/deps/py3.12`). Never into the active venv: a project venv gets pruned by `uv sync`, and a bound kernel's prefix is an ephemeral `uv run` overlay that differs on every invocation. Versioned because the directory goes on `sys.path` for any interpreter and compiled wheels are built for one minor version; `ensure_deps_on_path()` *appends* it, so the project's own packages always shadow a gist dep. Every import is recorded in a central registry (`~/.config/repld/gist-registry.json`, name → path/project/last_used). **Cross-project links (`gist_links.py`):** `repld gist add <name>` resolves a registered gist's path, AST-follows its same-dir sibling imports, and records absolute paths in a committed `./gists/.links` manifest — without copying. At boot `_load_links()` populates the `_linked` name→path overlay (consulted by `_GistFinder` + `_iter_gist_files` *after* local dirs, so local gists always shadow); stale entries are skipped (never auto-rewritten — the manifest is committed). `repld gist list` shows local + linked (flagging stale), `repld gist rm <name>` / `rm --stale` unlink. **`repld gist fetch <gist-url>` is `new`'s sibling, not `add`'s** — it *copies* a GitHub gist's `.py` files into `./gists` (or `~/.repld/gists` under `--global`) with a `# source:` header, so nothing tracks the gist afterwards and `rm`, which only unlinks, is not how you undo it. It enforces the same three collision scopes as `add_link` (local, global, already-linked) for the same reason — including the third, which `add_link` itself was missing: the manifest is a flat name→path map, so a co-linked sibling could silently repoint a name another linked gist depends on, reported as nothing but `+ siblings: <name>`. All three commands refuse it now, and deliberately does *not* install the fetched file's `__repld_deps__` the way `add` does: `add` links code you wrote in another project, while this is code from a URL whose dependency list should not drive an install before the file has been read. It accepts a bare gist id, a `gist.github.com` URL, or a raw `gist.githubusercontent.com` one (`_GIST_HOSTS`), and refuses everything else — the file lands somewhere a kernel imports at boot, so the set of origins should be one a reader recognises. The three modules share helpers via an intentional call-time-attribute import cycle (`gists._parse`, `gists.registry`, `gist_links._linked`, ...). **`gist_api.py` sits underneath that cycle rather than inside it:** it is the AST-in, API-text-out half — `_parse` and the `_format_*` renderers behind `repld://gists/{name}`, the MCP instructions and `repld gist list` — and it touches none of `gists.py`'s mutable hook state (`_managed`, `_mtimes`, `_installed_dirs`, the registry), so it imports nothing from repld and can be imported outright. `gists` re-exports `_parse` and `_dunder_value` because `gist_links`, `gist_deps` and `gist_lint` reach them as `gists._parse` / `gists._dunder_value`; that is the cycle contract above and it holds whichever module defines them. Note what that means for monkeypatching, the same rule the browser split carries: a test patching `gist_api._parse` is patching the definition, and `gists` resolves it through its own namespace — `phase_3_patch_targets` is the sweep that catches the mismatch.

## Architecture (target shape)

Eleven CLI subcommands, all dispatched from `repld:main`:

- `repld` — long-running Python kernel for the cwd, with the live TUI display. Takes the project's flock mutex (`kernel.flock`) and writes `kernel.lock` with `{pid, socket_path, cwd, started_at, dashboard_port}`; listens on a unix-domain socket. Losing the flock is not an error — it prints a note and exits 0 so the incumbent is adopted, never raced. No flags select a project bootstrap: a `repld_init.py` in the cwd is auto-detected (see the invariant below).
- `repld bridge` — stdio MCP subprocess Claude Code spawns for a registered repld server. Inherits cwd, attaches to a kernel that's already running or lazily spawns one on first real use, proxies stdio MCP ↔ the kernel's IPC socket, and relays channel notifications (`notifications/claude/channel`) back to the client. See the slim-loader invariants below. `repld bridge --ephemeral` inverts both halves for a private, single-use kernel: it spawns eagerly (before the first message, not on first real tool call) at a private socket path outside `PROJECTS_DIR`, and kills it (SIGTERM, SIGKILL after `WAIT_STEPS`) plus reclaims its whole directory the moment stdin closes, instead of leaving it running for the next session to attach to. Still `spawn.spawn_headless` underneath, spawned with `cwd=os.getcwd()` regardless of the socket override — so `./gists`, `repld_init.py`, `.env`, and `.venv` binding all resolve exactly as they do for the persistent kernel; only the state addressing is one-off. Mutually exclusive with `--socket`, enforced for free: skipping `resolve_socket_path` for this branch means a stray `--socket` just falls through to `check_args` as an unrecognised flag.
- `repld log` / `status` / `stop` / `restart` / `dashboard` — observe and control a kernel this terminal never started (`log_cmd.py`, `lifecycle_cmd.py`, `dashboard_cmd.py`).
- `repld gate` — list pending human gates, `repld gate answer <id> <value>` resolves one (`gate_cmd.py`). The headless kernel's answering surface; see the gate invariant below. Shares `exec_cmd`'s `_connect`/`_call` rather than keeping a second copy of the IPC handshake. **It is the one subcommand whose argv has a region no flag parser may enter:** an `ask` answer is free text, and all three parsers that run here reach across the whole list by design — `paths.resolve_socket_path` consumes `--socket PATH` from anywhere, `--json` was filtered the same way, and `cli_args.wants_help` scans every argument on purpose (that is what makes `gist rm foo --help` ask for usage). So `repld gate answer <id> deploy --socket now` answered `"deploy now"` and silently repointed the connection at a kernel called `now`. `_split_answer` cuts argv at `answer <gate_id>` before any of them run; everything past that is the answer verbatim, and flags for the command go *before* the verb. The `[--socket PATH]` the usage used to show trailing `<value>` is gone with it — it was never distinguishable from an answer that says the same words.
- `repld help [TOPIC]` — agent-facing docs. Single source of truth shared with the MCP `initialize` `instructions` field (composed by `src/repld/help.py:build_instructions()`). Never let the two drift.
- `repld exec [CODE]` — human-facing CLI. With no args, interactive REPL over IPC (shared namespace). With a string arg, one-shot execution. Same kernel, same state as the agent.
- `repld gist` — command group: `new <name>` (scaffold `./gists/<name>.py`), `fetch <gist-url>` (download a GitHub gist's `.py` files into `./gists`, or `~/.repld/gists` with `--global`), `add <name>` (link a registered gist from another project), `rm <name>` / `rm --stale` (unlink), `list` (local + linked + linkable-from-registry), `lint [--local] [name...]` (AST checks — docstring first line, return-shape docs, undeclared `__repld_deps__`, legacy tool API; `gist_lint.py`, suppress with `# gistlint: ignore=<rule>`). Lint's default scope is everything a kernel here would import — global + local + linked, and unlike the rest of the gist commands that includes private (`_`-prefixed) files, which are importable and so can carry real dep/shape problems even though they're never exposed as gists. `--local` narrows to `./gists` so the exit code is usable as a gate for one project, and resolves names against that directory first rather than through `_find_gist`, whose precedence is the kernel's (global before local) — otherwise a global gist sharing a stem made `lint --local <name>` reject a file the no-argument form lints happily. Lint is read-only, so it calls `gists.install(..., create=False)`: it needs the name resolution, not the boot-time side effect of bringing both gist directories into being in a project that has neither. Unknown verbs error (no verb-less scaffold alias), and every verb rejects flags and surplus positionals it doesn't understand via `cli_args.check_args` — only `fetch` and `list` used to, so `gist new x --global` silently ignored the flag its sibling honours. Top-level CLI dispatch is a single `_SUBCOMMANDS` table in `cli.py` driving both dispatch and `--help`.
- **Subcommand argument validation lives once, in `cli_args.py`.** `check_args(prog, argv, usage, flags=, positionals=)` refuses unrecognised flags and surplus positionals; `wants_help` scans *every* argument for `-h`/`--help`, not just the first, so `gist rm foo --help` asks for usage instead of unlinking foo. It's a separate module from `cli.py` because that one routes *between* subcommands — a command module importing its own dispatcher to borrow an argv helper would be backwards. Both checks were solved once in `gist_cmd` and then open-coded again in `stop`, `restart`, `status`, `dashboard`, `gate`, and `help`, which is six places for the next flag to be forgotten in — `help` checked only `argv[0]`, so `repld help gists --help` printed the gists topic instead of usage. The last holdouts were `repld bridge`, which validated *nothing* — it discarded `resolve_socket_path`'s residue into `_`, so `--help` started a proxy that blocks on stdin forever and a typo'd flag in an MCP registration was silently ignored, on the one command with no terminal to notice — and `gist_cmd` itself, the file the helper was extracted *from*: `run_gist`'s group-level `argv[0] in ("-h", "--help")` sent `gist badverb --help` to "unknown command" instead of usage, and `fetch` refused unknown flags in a wording no other subcommand uses, and `list` kept a byte-identical copy of the surplus-positional check. A verb whose flags take a value calls `check_args` *after* consuming them — `fetch` strips `--name NAME` first, the same ordering every client subcommand uses for `--socket` — and passes no `flags=`, since by then anything still starting with `-` is unknown by construction. `check_args` rejects only *surplus* positionals, so a verb that requires one still needs its own `if not argv` after the call, as `add` has always had. `log_cmd` deliberately stays out: `-n N` takes a value, so its argv needs a real parser loop rather than a flag-set membership test.
- `repld browser [ARGS...]` — re-exec `repld ARGS...` under `uv run` with the `browser` extra (`duckdb` + `websockets` + `pillow`; all three are required, and all three are imported eagerly — `browser/png.py` pulls in PIL at module scope for `Tab.screenshot`'s resize, so installing only the first two leaves `kernel._inject_builtins` swallowing a `ModuleNotFoundError` and reporting the extra as absent), so browser features work without adding `repld-tool` to the project's dependencies. Preserves a local editable checkout (detected via `direct_url.json` distribution metadata) instead of silently falling back to the published package, so dev changes are picked up (`src/repld/relaunch.py`).

Key invariants to preserve when building this out:

- **One process, one asyncio loop.** The kernel owns a single shared loop so `asyncio.create_task(...)` from any exec call survives past the exec return and can push to channel on completion.
- **A lock taken across a CDP command must have an unlocked core, because the command can re-enter it.** `BrowserSession.execute` reconnects and retries on a dead socket, and `_reconnect` → `_reattach_core` re-enables the session's domains and its Fetch capture — on the *same task* that issued the command. So any `async with self._lock:` wrapped around an `execute` is reachable from inside itself, and `asyncio.Lock` is not reentrant: it deadlocks outright, with no traceback and no timeout, on a loop that is the whole kernel. Both locks on that path are split the same way — `reattach_session` wraps `_reattach_core`, `enable_fetch` wraps `_enable_fetch_core` — and the reconnect path always calls the core. Phase 6 asserts the non-deadlock directly; the control in that test confirms the wrapper version hangs.
- **`exec` returns fast or defers, and which one it did is decided once.** If user code finishes within `timeout` (default 2s) return inline; otherwise return `{task_id, done: false}` and push a channel notification on completion. The two are settled by `tasks.mark_nudged`, which takes the promise of a push under `_tasks_lock` and refuses it if the cell already finished — including inside the window `_exec`'s own `snapshot()` opens, which re-reads the entire spill file. It returns whether it got the promise, and `_exec` answers with the result when it didn't; `claim_done_push` is the paired read on the finalize side. Deciding these separately meant a cell landing in that window got neither: no push, and a reply saying one was coming. Every cell with output spills to `$XDG_RUNTIME_DIR/repld/{pid}-{tid}.out` from byte 1; the inline response carries a head+tail preview and the absolute spill path. Agents use the standard Read/Grep tools on that path — there is no `read_spill` MCP tool.
- **Stdlib only in core.** Zero required runtime dependencies. Optional extras (`repld[pretty]` for rich-rendered display) gate anything heavier. Don't pull new deps into the base package.
- **Per-cwd, localhost-only — and localhost is not a uid boundary.** The IPC socket stays on `127.0.0.1` or a user-only unix socket. This is a dev-time tool; never add anything that would make it safe to expose. Loopback keeps other *hosts* out, not other *users*: the unix socket is uid-protected by its mode, but the dashboard's TCP port is reachable by anything running on the box, which is why its token gates `GET /` and not just `POST /api`. Every file backing this data is 0600 for the same reason. When adding a surface here, the question is which of the two protections it actually has.
- **Runtime state lives under XDG, never in the project.** `paths.py` is the single source of truth (and, though they are source rather than state, it also owns the two gist directories — `global_gists_dir()` / `local_gists_dir()` / `gist_dirs()`, the last being the kernel's own import precedence; they were derived by hand at fourteen sites across `gist_cmd`, `gists`, `gist_links` and `kernel`, one of them carrying a "same dirs + precedence a live kernel resolves against" sync note): `$XDG_RUNTIME_DIR/repld/projects/{basename}-{sha256(realpath)[:8]}/`, created 0700. Every file is the socket path with a different suffix (`kernel.sock` → `.lock` / `.flock` / `.dashboard` / `.events` / `.cache`), so `--socket` / `REPLD_SOCKET` moves the whole set coherently. `kernel.cache` (`paths.cache_for`) holds the last-computed `initialize`/`tools/list`/`resources/list` triple (`protocol.build_discovery_cache()`), written once at boot and deliberately never cleaned up at shutdown — it's what lets the *next* bridge answer MCP discovery before a kernel exists (see the lazy-spawn note below). Per-process scratch is the one exception — task spills, resource spills, and browser screenshots belong to the process, not a project, and sit directly in `RUNTIME_DIR`. Every one of them is named `{pid}-…`, which is what lets a booting kernel reclaim a dead pid's leftovers in one pass (`state.sweep_dead_pid_files`, called from `_boot_runtime`); keep the prefix on anything new you write there, or neither reclamation rule will find it. **There are two rules, and both are needed.** The boot sweep can only ever collect *dead* pids, which is no help to a process designed to stay up for weeks, so a live kernel ages out its own: task spills by their registry entry (`tasks._prune_spill_files`, `_EVICT_AGE`), and everything with no registry entry — `tasks.spill_text`'s oversized resource/browser-tool responses, `Tab.screenshot`'s PNGs — by mtime at the same bound (`state.sweep_own_stale_files` via `tasks._sweep_orphans`). Anything new that writes here either goes through the task registry or inherits the orphan sweep for free; don't add a third scheme. Don't reintroduce a project-directory fallback.
- **Nothing under `RUNTIME_DIR` is readable by other users.** Without `XDG_RUNTIME_DIR` the root falls back to `/tmp/repld-{uid}` — uid-suffixed so it can't be pre-created and owned by someone else. `paths.ensure_runtime_dir()` is the only thing that creates that root; call it before writing anywhere beneath. `kernel._claim_project` is the earliest thing that writes there and now calls it first: `state.acquire_lock` does its own `mkdir(parents=True, mode=0o700)`, and with `--socket`/`REPLD_SOCKET` pointing under the root nothing had ensured it, so the root could come into being at umask default and skip the foreign-owner refusal. It exists because `Path.mkdir(parents=True, mode=…)` applies the mode *only to the leaf*, so a root brought into being as an implicit parent comes out 0755. Every state file is created 0600 up front (`state.open_private`, or `atomic_write_json(chmod=0o600)`) — never `open()` then chmod, which leaves a window at 0644.
- **One kernel per project, enforced by flock.** `kernel.flock` is opened `O_CREAT` *without* `O_TRUNC` and never replaced — `kernel.lock` is rewritten atomically via `os.replace`, which would move the inode out from under a flock held on it. That's why they're two files.
- **The kernel binds itself to the project's interpreter; it is never spliced across versions.** `bind.py` is the single answer to "which Python should we be". Installed as a uv tool, repld's console script pins its own interpreter via the shebang, so a kernel would otherwise be unable to import the project it sits in. Entry points that run or create a kernel (`repld`, `bridge`, `restart`) call `bind.rebind_exec()` first, which re-execs through `uv run --with-editable`/`--with` under the project venv's Python; `exec` is deliberately excluded — it only resolves a lock path and talks IPC, and the code it runs executes inside the kernel, which is already bound. `REPLD_BOUND` is the sentinel that stops `uv run … repld bridge` re-entering forever, and `is_bound()` is the semantic check (is the venv's site-packages on `sys.path`?) rather than a prefix comparison, because under a uv overlay `sys.prefix` is a cache directory. **Only a version-matched venv may be `addsitedir`'d onto a running kernel** (`bind.adopt`) — a venv's compiled extensions are built for one minor version while its pure-Python and `abi3` packages import anywhere, so splicing a mismatched one half-works, and a partial success is worse to debug than the clean refusal plus the enriched `ModuleNotFoundError` that `gists._explain_missing` raises instead. `project_venv()` prefers `./.venv` over `$VIRTUAL_ENV`: cwd identifies a project everywhere else in repld, and an ambient `$VIRTUAL_ENV` belongs to whatever shell launched the client, not necessarily to this project.
- **A few tools are served by the bridge, and the split is narrow on purpose.** `bridge_tools.py` holds them; a tool belongs there *only* if it must work while the kernel is dead or if it kills the kernel (`repld_restart` is both). Everything else goes in `protocol.py`, or the bridge accretes into a second, worse kernel. The wiring is deliberately one-directional: the kernel advertises `bridge_tools.SCHEMAS` from `_tools_list`, and the bridge intercepts the matching `tools/call` on the *request* side, before the liveness ladder. It never rewrites a response — see the byte-pipe note below. `protocol._tools_call` carries a matching branch that errors by name, since a bridge tool arriving at the kernel means the client connected to the socket directly.
- **Anything both sides of the socket answer lives in `core_schemas.py`.** The bridge answers `initialize` / `tools/list` / `resources/list` itself whenever no kernel has ever run in the project, so every one of those responses has two authors — and a constant declared in only one of them is silently wrong for exactly the sessions that start cold, which is the case nobody is looking at. `CORE_TOOLS`, `DOC_RESOURCES`, `DOC_HELP_ATTRS`, `REGISTRY_RESOURCE`, `STATIC_RESOURCES`, `RESOURCE_TEMPLATES`, `CAPABILITIES`, `PROTOCOL_VERSION`, `SUPPORTED_VERSIONS`, and `negotiate_version` are all there for that reason, as are the `response`/`error`/`notification` envelope builders — the bridge wrote those by hand at ten sites because it cannot import `protocol.py`, which is the same constraint that put everything else here; the module stays pure stdlib data so the bridge can read it without pulling in the kernel's dependency chain. `STATIC_RESOURCES` is what both sides actually serve — `DOC_RESOURCES` plus `REGISTRY_RESOURCE`, which is kept *out* of `DOC_RESOURCES` because that list drives `DOC_HELP_ATTRS` and the registry has no `help.py` attribute behind it. It was declared inline in `protocol.py` until it turned out cold sessions were never told the resource existed. Note that `initialize` actually has *three* authors, not two — `repld exec` handshakes over the socket itself — which is why `PROTOCOL_VERSION` belongs here rather than in `protocol.py` with a hand-sync comment on each copy. **Version negotiation is echo-what-they-asked-for**: `negotiate_version` returns a requested version we support verbatim and our latest otherwise (never echoing an unknown string), and both `initialize` authors call it — the bridge deliberately does *not* read the cached kernel answer for this, since that was negotiated with a different session's client. 2025-06-18 is the deliberate ceiling: everything repld uses from it (tool annotations, `structuredContent`/`outputSchema`, resource templates) is additive, which is what makes serving the older revisions from one code path correct; 2026-07-28 removes the `initialize` handshake outright and is a bridge rearchitecture, not a bump. `get_task`'s declared `outputSchema` commits `_get_task` to a conforming `structuredContent` on every success — the shape is `tasks.snapshot()`, so a field added there must be added to the schema. `CAPABILITIES` matters most: both parties may only use what was negotiated at `initialize`, so a drifted copy *disables* a feature rather than degrading it — `listChanged` is what lets the bridge invalidate the client's tool list after respawning a kernel. `build_discovery_cache()` deliberately doesn't carry it, so a warm `kernel.cache` can't paper over a drift either. Phases 3 and 15 assert both paths negotiate exactly `core_schemas.CAPABILITIES`. The `instructions` field is the same problem in prose rather than data, and it lives in `help.py` instead: `static_instructions()` is `build_instructions()` minus only what needs a live kernel (browser model, gist listing, registered gist tools), composed from the same constants in the same order and kept adjacent to it. It was `_EXEC_MODEL` alone, which meant a cold session — the one deciding how to structure the work — was never told `./gists` existed, and nothing re-sends `instructions` after the lazy spawn.
- **The bridge is a stateful proxy, not a byte-pipe.** It must never close its own stdout (MCP client dispatchers are single-shot and cannot re-handshake), must cache the client's `initialize` and replay it onto every fresh kernel (a respawned kernel is uninitialized and would queue channel pushes forever), must answer orphaned in-flight ids with `-31001`, and must probe liveness *before* forwarding rather than retrying after a failure — `exec` runs arbitrary code and must never run twice. Diagnostics go to stderr only.
- **Kernel spawn is lazy, but only when there's genuinely nothing to attach to.** `Bridge._handle_client_line` first tries a cheap, no-spawn connect (`_try_attach_existing`) — if a kernel for this project is already running (the common case: a second window, a kernel a prior session left up), it attaches for free and every request forwards live, exactly as before. Only when that fails does MCP discovery fall back to `kernel.cache` (`_try_bridge_intercept`), and only a real `tools/call` or gist/browser `resources/read` triggers `_ensure_kernel`'s actual spawn-and-wait. That last part is enforced by `_NEEDS_KERNEL`, not by exhaustion: anything the intercept declines that isn't one of those two is answered `-32601` by the bridge, and an unparseable line is dropped. Both used to fall through to the spawn, so a client-side `ping` or one truncated stdin line paid the full 5 s spawn-and-wait for a method no kernel of ours implements. `notifications/initialized` is tracked (`_client_initialized`) rather than always replayed on first spawn — replaying it early, before the client genuinely sent it, would let a channel push escape the kernel's pre-init queue ahead of schedule. `--ephemeral` is the one deliberate exception to "lazy": its whole premise is a kernel for exactly this session, so `run()` calls `_ensure_kernel()` before reading stdin at all — which also means `initialize` itself forwards to a live kernel instead of `_try_bridge_intercept`'s cache/static answer, since that path is only taken while `self._sock is None`.
- **The project bootstrap is a file, not a flag.** `kernel.INIT_FILENAME` (`repld_init.py`) is auto-detected in the kernel's cwd and executed into `__main__` at boot — the same shape as `_load_dotenv()` reading `./.env` and `gists.install()` putting `./gists` on `sys.path`, and for the same reason: the project directory is the source of truth. It was `--init FILE` until 0.2, which only ever fired for a hand-started kernel that won the flock; `spawn._kernel_argv` carries `--no-display` and nothing else, and the lockfile records no init path, so the bridge's lazy spawn, `repld restart`, and `repld_restart` all silently dropped it — on precisely the projects (a kernel hosting a server) that are useless without it. Two ordering rules: it runs **after** `_start_services` binds the socket, because the bridge only waits `WAIT_STEPS × WAIT_STEP_SECONDS` (5 s) for a spawn to become connectable and a bootstrap that raises a tunnel takes longer — booting it first would time out lazy spawn on exactly the projects that have one; and `_run_init_file` must **never raise**, including on the file read, since a failed bootstrap needs a live kernel to be fixed from. `./.env` is read once at boot too, and unlike `./gists` it does not reload on mtime — `load_dotenv` is public (`from repld import load_dotenv`) so a value written afterwards can be picked up, and it still never overrides an existing var, so a name captured while empty must be cleared before reloading. It pushes `init_loaded` on success (the only signal that a bridge-spawned kernel came up pre-populated) and `init_error` on failure. **`_run_cell` waits on `_init_done` before running any cell**, which is what stops the first `exec` after a lazy spawn from racing the bootstrap and finding a bare `__main__`; the wait lives there rather than in the socket bind so lazy spawn keeps its 5 s window, and the flag is set unconditionally after `_run_init_file` returns — a bootstrap that failed, timed out, or never existed must still let `exec` through, since a kernel nobody can run code in cannot be repaired. The bootstrap cell itself passes `wait_ready=False`, or it would wait on its own completion. **`exec` is not the only lazy-spawn trigger, so it is not the only waiter.** `_NEEDS_KERNEL` also spawns on a gist or browser `tools/call`, and those answer inline or not at all — there is no `{task_id, done:false}` for them to degrade into — so `protocol._tools_call` blocks on `_Context.wait_ready()` before dispatching either. That wait is on the IPC thread rather than the loop, which is exactly why `exec` must *not* come through it: `_run_cell`'s await is what lets a cell take its task_id immediately and turn a slow bootstrap into an ordinary completion push. Both are bounded by the one `_INIT_WAIT_SECONDS`, which is also the budget `_run_init_file` gives the bootstrap — so no waiter can outlive the thing it waits for.
- **A human gate must stay answerable on a kernel with no pane.** `ask`/`confirm`/`choose` park a cell until something calls `gates.resolve_gate`, and there are exactly three callers: the TUI's stdin reader, a pinned tab's pill, and `repld gate answer` (via the kernel-side `gates/list` + `gates/resolve` JSON-RPC methods in `protocol.py`). Only the third exists on an auto-spawned kernel — `--no-display`, stdin on `/dev/null` — which is the common case since lazy spawn, so anything that adds a gate surface must keep that route working. They race and first-wins; `resolve_gate` returns whether *this* caller was the one that answered. Coercion lives once in `gates.parse_response` so a pane and the CLI can't disagree about what `y` or `2` means — an index has to resolve to the option, not to the literal string. The two *boot* prompts (restoring a browser session, installing gist deps) ask before the loop, the display or the tee exist, so they go through `gates.tty_prompt` rather than a gate — but they share the vocabulary via `gates.yes_by_default`, which is `_YES` plus the empty-string default a `[Y/n]` prompt needs. Each kept its own `in ("", "y", "yes")` until that existed, accepting *less* than a gate does, so `1` and `true` declined the browser-restore prompt while confirming a `confirm()`. **The pane's claim on stdin is released when its reader ends**, not just taken when it starts: `_stdin_owned` set true and never set back meant that after an EOF on a redirected stdin, `tty_prompt` declined for the rest of the process's life and `gist_deps` blamed a thread that had exited. `gates/list` and `gates/resolve` are deliberately JSON-RPC methods and **not** MCP tools: an agent able to answer its own `confirm()` defeats the primitive. When `gates._has_terminal` is false and no pill is in play, the `awaiting_human` push carries the literal `repld gate answer` command, because the agent is what reads that push and the human is what needs the command. "No pill is in play" is a question about `kind` as much as about pinnedness: the pill is a row of buttons with no text input, so `_show_gate` renders `confirm` and `choose` and returns without drawing for an `ask`. Deciding on pinnedness alone made `tab.ask()` suppress the command *and* show nothing — the one combination with no surface at all. **A gate that ends without an answer is announced, not just forgotten:** `timeout=` expiring (the documented way to stop a gate parking a cell indefinitely) and the awaiting cell being cancelled both close a gate with `resolve_gate` never called, so `_gate`'s `finally` emits `HumanPromptClosed(gate_id, reason)` alongside popping it. `gates._gates` *is* what `open_gates` reads, so `repld gate` self-corrects — but every surface that keeps its own mirror of the open set learns only from an event, and the pane keeps one (`display._open_gates`). Without the event its entry stayed forever, and since `_stdin_reader_loop` routes to the *newest* open gate, the pane's stdin went dead: every line typed resolved a gate the kernel had already dropped, silently. `_Gate.answered` rather than an inspection of the future is what tells the two endings apart — a cancelled future is indistinguishable from one whose `set_result` lost a race — and `resolve_gate` claims it *before* `set_result`, releasing it again on `InvalidStateError`, or a losing caller could mark a just-expired gate answered and suppress the close event entirely.
- **The pane's stdin has exactly one reader, and `tty_prompt` is boot-only because of it.** `gates.tty_prompt` is the synchronous sibling of the gate primitives — it talks straight to the controlling terminal for the two things that must ask before the loop, the display or the tee exist (installing gist deps, restoring a browser session). Past boot it must not run at all: `display._stdin_reader_loop` is parked in `readline()` on that same `sys.__stdin__` and consumes every line whether or not a gate is open, so a second reader blocks behind its buffer lock while the reader discards the answer. That is not hypothetical — `gist_deps.install_deps` is also reached from `gists._check_reload` / `_scan_new_deps`, i.e. from `builtins.__import__` inside a user cell, and on an `await` cell that *is* the shared loop; the watchdog's cancel then has no await point to land on, so the kernel wedges until a human types something. `gates._stdin_owned` (set by `run_display`, distinct from `_has_terminal`, which is set at the top of `_boot_runtime` and answers "will a pane exist") makes `tty_prompt` return None past that point, which every caller already handles as "nobody to ask". `_has_terminal` is not a substitute: it is already true during the boot prompt, so gating on it would kill the one call that is supposed to work. Anything new that reads stdin directly asks `stdin_owned()` first.
- **Targeted push for call-scoped output, broadcast for ambient.** A task carries the `ipc.Session` that started it (`task["origin"]`); `_maybe_push_done` routes its completion there. `@every` errors, console errors, browser connect/disconnect, and bare `notify()` stay broadcast. If the origin disconnected, drop the push — never fall back to broadcast. The local `events.emit(ChannelPush(...))` fires either way, so `repld log` still sees it. **Which of the two a piece of output is gets decided by `tasks._current_task`, and anything that outlives a cell has to say so.** `_task_scope` is the only thing that binds it, wrapping `_run_cell` and `_run_deferred` — both of which end, which is what makes inheritance right for them: a `create_task` or `defer()` from a cell body is that cell's work, and `copy_context()` carrying the id is the feature. A `@every` ticker goes through neither and outlives the cell by weeks, so inheriting silently made it call-scoped forever. Every cap downstream keys on that id and is cleared only by the owning cell's `CellDone` — `display._truncated_tasks`, `eventlog._chunk_capped`, and the spill handle `finalize` deliberately leaves open — so the ticker filled a *finished* cell's 4 KB budget and was then dropped permanently by the pane and by the event log, which on a headless kernel is the only surface there is; an hour on, `_prune_spill_files` unlinked the file and the writes went nowhere at all. `_start_ticker` clears it (`tasks.set_current_task(None)`) so ticks render unattributed and uncapped, like the boot banner. The rule for anything new: if it can still be running after the cell that created it returned, it is ambient and must clear the id rather than inherit one.

## Design principles (from README)

- **Substrate, not library.** Expose small composable primitives (`notify`, `defer`, `@every`, `browser.watch`, `browser.get`) and let the LLM write integration code against live pages/APIs/DBs. Resist adding per-service helpers.
- **Channel push over polling.** Long jobs, file watchers, webhooks, and timers all surface as `<channel>` injections rather than requiring the agent to poll.
- **Shared `__main__` namespace.** Human and agent operate on the same module dict — don't sandbox the agent into an isolated scope.
