# Changelog

All notable changes to this project will be documented in this file.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Lazy kernel spawn.** Opening a Claude Code session in a repld-configured project used to spawn a kernel immediately — before the agent ever called a repld tool. Now the bridge only pays that cost when it's actually needed: if a kernel for the project is already running it attaches for free, exactly as before; if none exists at all, MCP discovery (`initialize`, `tools/list`, `resources/list`, and the four static doc resources) is answered from `kernel.cache` — a small file each kernel writes at boot with its computed instructions, tools, and resources — or a minimal static fallback (`exec`/`get_task`/`cancel` plus bridge tools) on the very first run in a cold project. Only a real `tools/call` or a gist/browser `resources/read` triggers the actual spawn-and-wait, and the existing `notifications/tools/list_changed` / `notifications/resources/list_changed` mechanism reconciles any staleness once the kernel comes up. A version-mismatched cache (left by a different repld release) is discarded rather than trusted
- **Headless kernel.** `repld bridge` is now a slim loader: when Claude Code connects and no kernel is running for the project, it spawns a detached headless one and waits for it to answer. Starting `repld` by hand first is no longer required — do it only when you want the live TUI display. The kernel it spawns persists until explicitly stopped, so in-memory state survives a Claude Code restart
- **Self-healing bridge.** If the kernel dies mid-session the bridge no longer exits with it. It answers each orphaned in-flight request with a `-31001` error (rather than leaving the client hanging), then re-spawns and reconnects on the next inbound request, replaying the client's cached `initialize` + `notifications/initialized` onto the fresh kernel so channel pushes keep flowing, and emitting `notifications/tools/list_changed` + `notifications/resources/list_changed`. It never closes its own stdout: MCP client dispatchers are single-shot and cannot re-handshake, so a bridge that exited on kernel EOF would end the session permanently. Liveness is probed *before* forwarding, never by retrying a failed request — `exec` runs arbitrary user code and must never run twice
- **One kernel per project, enforced by flock.** A second `repld` in the same project now prints a note and exits 0 instead of failing, so a racing bridge (or a human) simply connects to the incumbent. An externally-started or supervised kernel is adopted, never competed with
- `repld log [-n N] [-f] [--json]` — replay or follow a headless kernel's activity (cells, output, channel pushes) from any terminal, rendered the way the TUI renders it. Backed by a new NDJSON event log written next to the socket; previously `--no-display` mode discarded every event and nothing persisted
- `repld status [--json]` — this project's kernel (pid, uptime, socket, dashboard URL, active tasks/tickers) plus every live kernel elsewhere, so auto-spawned kernels in other projects are visible rather than silently accumulating
- `repld stop [--all]` / `repld restart` — lifecycle control for kernels you never started
- `repld dashboard [--print]` — resolve the running kernel's dashboard port and open it, printing the URL when a browser can't be opened
- `python -m repld` entry point (`src/repld/__main__.py`), which is how the bridge spawns kernels
- **The kernel now runs as its own systemd user service where systemd is available**, instead of as a detached child of whoever spawned it. `start_new_session` detaches from the *controlling terminal* — closing the window won't SIGHUP the kernel — but it neither reparents the process nor moves it out of the spawner's cgroup, so a bridge-spawned kernel stayed a child of that bridge and shared the terminal window's cgroup. Everything it loaded (model weights, a browser) was accounted to that window. It now goes to the user manager as `repld-<slug>-<hash>.service`, so it gets its own cgroup, its own lifetime, and — the practical win — **its stdout and stderr in the journal**: `journalctl --user -u 'repld-<slug>-*'` is the only place a bridge-spawned kernel's boot failure could ever be read, since it has no terminal. The unit is keyed off the resolved socket path, like every other piece of per-project state, so a `--socket`/`REPLD_SOCKET` override moves it with the rest and two kernels sharing a cwd can't collide on one unit name; the readable prefix is the socket's parent directory basename, which for the default socket is `paths.project_slug`. A *service*, not a `--scope`: a scope runs in the caller's own context and would keep both the parentage and the caller's environment. Any systemd failure falls back to the previous detached-child path, so spawning is never less reliable than before; non-systemd hosts are unaffected. Two opt-in knobs come with it — `REPLD_MEMORY_HIGH` (a `MemoryHigh=` ceiling) and `REPLD_OOM_SCORE_ADJUST` — both off by default because each overrides a deliberate policy. **This does not change how likely a kernel is to be OOM-killed:** the user manager's `DefaultOOMScoreAdjust` is 200 on a stock session, the same value a Claude Code client passes down, and under global OOM the killer picks by RSS anyway, so a kernel holding several gigabytes is still first in line
- **The kernel now binds itself to the project's virtualenv**, so code in `exec` can import the project it's sitting in. Installed as a uv tool — the recommended way — repld's console script has its interpreter baked into the shebang, so the kernel ran under the *tool's* Python no matter which project it was started in, and `import <your package>` failed. `.mcp.json` didn't help: `repld init` emitted `uv run repld bridge` whenever a `uv.lock` existed, but `uv run repld` only reaches the project's interpreter if `repld-tool` is a project dependency, which repld's own docs tell you not to add — so it fell through to the same console script on `PATH`, after a per-session `uv sync` that bought nothing. New `bind.py` re-execs through `uv run` under the project venv's Python before the kernel starts, preferring a local editable checkout exactly as `repld browser` does. `repld init` now always writes the plain `repld bridge` form, and existing `.mcp.json` files need no change
- **A version-matched venv appearing after boot is adopted live; a mismatched one is refused with an explanation.** When the project's Python minor version matches the running kernel, its `site-packages` is spliced on with `site.addsitedir` (which also picks up editable installs' `.pth` finders) and a channel message says so. When it doesn't match, `sys.path` is left strictly alone: a venv's compiled extensions are built for a single minor version while its pure-Python and `abi3` packages import anywhere, so splicing a mismatched one half-works — some project packages import, others fail — which is harder to diagnose than a clean refusal. Instead the failing import carries the reason: *"No module named 'partbridge' — but 'partbridge' is installed in …/.venv (Python 3.12), and this kernel is Python 3.13 … call the repld_restart tool to rebind"*. `repld status` grew a `python:` line that flags the same mismatch, and the lockfile records the interpreter
- **`repld_restart` MCP tool** — restart the project's kernel from inside the conversation, instead of leaving the session for a terminal. The MCP session survives: the bridge respawns the kernel and replays the cached handshake, so tools keep working and channel pushes keep landing. In-memory state (variables, `@every` tickers, browser connections) is discarded, which is the point of the call. Served by the bridge rather than the kernel — a kernel cannot answer "restart yourself", since the reply would still be in flight when the process goes away and the client would see `-31001` for an operation that had in fact succeeded. New `bridge_tools.py` is the registry for this narrow class of tool: the kernel advertises the schemas in `tools/list` and the bridge intercepts the matching `tools/call` before its liveness ladder, so no response is ever rewritten and the proxy stays byte-preserving
- **`repld_init.py` — a project bootstrap that every kernel runs.** A file of that name in the project root is executed into `__main__` at kernel boot, whoever started the kernel: you, the bridge's lazy spawn, or `repld restart`. Same shape as the `./.env` loading and `./gists` importing that already key off the project directory, and it replaces the `--init` flag (see Removed). It runs *after* the IPC socket binds, deliberately — the bridge allows a spawn 5 s to become connectable, and a bootstrap that raises a tunnel or waits on a port takes longer, so front-loading it would break lazy spawn on exactly the projects that have one. Two new channel kinds mark the boundary: `init_loaded` when it finishes (on a kernel nobody watched boot, that is the only sign `__main__` arrived furnished) and `init_error` with the traceback when it raises. A failing bootstrap never takes the kernel down — including one that can't be read, which previously killed boot outright — because a broken bootstrap is exactly when you want a live kernel to fix it from
- **Per-parameter descriptions for gist tools, via `Annotated[T, "..."]`.** A typed `_tool_*` function infers its whole schema from the signature and the docstring's first line — and that first line is spent on the *tool* description, so there was nowhere left to say that a parameter is a date in `YYYY-MM-DD`, or which endpoint an id came from. The legacy `__repld_tools__` list could express it by hand; nothing that replaced it could, which made the deprecation a quiet downgrade for any tool with a non-obvious argument. `Annotated[str, "From date YYYY-MM-DD"]` now becomes that property's `description`. Bare-string metadata rather than a `Field`-style object, since repld carries no runtime dependencies — it is the stdlib analogue of `Annotated[str, Field(description=...)]`. Composes with the existing unwrapping, so `Annotated[str | None, "..."]` still resolves to `string` with its default advertised; metadata that isn't a string is ignored rather than rejected, and an un-annotated parameter is completely unchanged. Purely additive — every existing typed gist keeps working untouched. `repld gist new` scaffolds with it
- **`repld gate` — see and answer the human gates a kernel is blocked on.** `ask()` / `confirm()` / `choose()` park a cell until a human answers, and until now only two things could deliver that answer: the stdin reader belonging to the live TUI, and a pinned browser tab's pill. A kernel spawned *for* you has neither — it runs `--no-display` with stdin on `/dev/null` — so on the kernel that lazy spawn made the common case, a `confirm()` blocked forever with no way to resolve it. `repld gate` lists what's pending (id, kind, prompt, how long it has waited) and `repld gate answer <id> <value>` resolves it, over the same IPC socket every other subcommand uses. `<value>` is `y`/`n` for a confirm, an option name or its 1-based number for a choose, and free text (unquoted, joined) for an ask. All three surfaces race and the first answer wins, as before. Deliberately *not* an MCP tool: an agent that could answer its own `confirm()` would defeat the primitive
- **The `awaiting_human` channel push now says when nobody can answer it.** On a kernel with no pane and no pinned tab, the push carries `no terminal attached — answer from the project dir with: repld gate answer <id> <value>`. The agent is what sees that push, so it is the thing that can hand a human the command instead of silently waiting. Gates also carry their id into `repld log -f`, which is where someone watching a headless kernel sees one open
- `repld gist lint --local` — restrict the check to `./gists`. The default scope is everything a kernel here would import, which is right for a manual sweep (a malformed docstring in a global gist pollutes *every* project's MCP instructions) but makes the exit code useless as a pre-commit or CI gate: a stale gist in `~/.repld/gists`, or in another repo you've linked from, fails the run with a finding you can't fix from inside this project. `--local` also scopes name resolution, so `repld gist lint --local <name>` errors rather than silently checking a global gist of that name

### Changed

- The kernel's boot banner advised `claude mcp add -s project` — the scope that writes a `.mcp.json` into the project. It prints the plain local-scope form now, matching the rest of the setup guidance
- **`exec` no longer runs a full garbage collection after every cell.** The collect existed to flush "coroutine was never awaited" warnings into the output of the cell that caused them, but it walked the entire heap to do it — measured at 164 ms per cell against 800k live objects, in a runtime whose entire premise is holding large state across many cells for weeks. It is now a generation-0 collection (~0.005 ms), which is where an abandoned coroutine actually is: the ordinary case never needed a collection at all (the refcount drops at cell exit and `__del__` fires on its own), and the cyclic case is a traceback holding the frame that created it, allocated moments earlier
- **The IPC socket is created 0600 rather than chmod-ed to it.** `bind()` applied the process umask and the mode was fixed immediately after, leaving a window in which the socket was connectable by any local user. Every other runtime file is created at its final mode for exactly this reason; the socket was the one node that wasn't. The 0700 project directory was and remains the actual barrier, so this closes a defence-in-depth gap rather than a live hole
- **Runtime state moved out of the project directory** into `$XDG_RUNTIME_DIR/repld/projects/{basename}-{sha256(realpath)[:8]}/` (created 0700), alongside the existing `sessions/` and task spill files. The socket, lockfile, dashboard hint, and new event log are all there as `kernel.sock` / `.lock` / `.flock` / `.dashboard` / `.events` — every file is the socket path with a different suffix, so `--socket` and `REPLD_SOCKET` still move the whole set together. New `paths.py` is the single source of truth; the `./.pyrepl.*` fallbacks are gone
- **Channel pushes caused by a specific request now go only to the session that made it.** A deferred `exec` completing (or a timed-out one finishing later) notifies the bridge that called it instead of every connected session; `defer()` inherits the originating session of the cell that called it. Genuinely ambient pushes stay broadcast — `@every` errors, watched-tab console errors, browser connect/disconnect, and bare `notify()` from shared user code. If the originating session disconnected before its task completed the push is dropped rather than downgraded to a broadcast, which would leak one session's output into every other one; it still reaches `repld log` and the task's spill file
- **A headless kernel no longer builds the display event queue at all.** `emit()` fans every event out to two destinations: the event log's sink, and a 10,000-slot queue that exists for the live TUI. With `--no-display` — how every auto-spawned kernel now runs — nothing consumes that queue, so it was initialized anyway and a `repld-drainer` thread was started for the sole purpose of throwing its contents away, costing two lock round-trips and a cross-thread wakeup per event (one event per stdout chunk, so several per `print()`). The drain thread was not optional given that design: an unread queue pins at capacity, after which every `emit()` takes the drop-oldest path, which is more work per event than draining. `run_kernel` now calls `events.disable_queue()` instead, `emit()` returns after the sink, and the drain thread is gone. No behavioural change — the event log, `repld log`, and channel pushes are all fed by the sink, which always ran first
- Codebase health pass: the four static doc resources were described in three places — their wire metadata in `core_schemas.DOC_RESOURCES`, and a URI→`help.py`-constant map in *both* `protocol.py` (kernel-side reads) and `bridge.py` (the cache-less fallback added this release), so adding one meant three edits and forgetting the bridge's copy would degrade quietly into a spurious kernel spawn rather than an error. The attribute name now rides on the resource entry itself (`DOC_HELP_ATTRS`), with a `wire()` helper stripping internal keys before anything reaches a client. `repld init` also joins the other subcommands' argument conventions — a `_USAGE` constant, a `repld init:` prefix on errors, usage reprinted on a bad flag, and `-h`/`--help` honoured anywhere in argv rather than only in first position
- The MCP `initialize` response now declares `listChanged: true` for tools and resources — a prerequisite for the bridge's post-respawn `list_changed` notifications, since both parties may only use negotiated capabilities. The capability block is one constant (`core_schemas.CAPABILITIES`) rather than a copy in `protocol.py` and another in `bridge.py`: the bridge answers `initialize` itself when no kernel has ever run in this project, and the discovery cache doesn't carry capabilities, so a capability added kernel-side would have been missing from exactly the cold-start sessions — and since both parties may only use what was negotiated, that disables a feature rather than degrading it. `PROTOCOL_VERSION` moved to the same module, from three hand-synced copies: `repld exec` handshakes over the socket too, so `initialize` has three authors, not two

### Security

- **`atomic_write_json(chmod=…)` now creates its temp file at that mode instead of chmod-ing it afterwards.** It is one of the two sanctioned ways to get a 0600 state file, and it was doing the exact thing the rule exists to forbid: `write_text()` creates at the umask default, so the temp briefly sat at 0644 holding byte-for-byte what the final file would — the dashboard's API token, the session registry's list of every project cwd and socket, the kernel lockfile. Its docstring's claim that "the final file never exists with wrong permissions" was true of the renamed path and false of the temp. Every affected file lives under a 0700 directory, so this closes a defence-in-depth gap rather than a live hole, in the same way the socket-creation fix above does. `state.open_private` grew a `perm` argument to serve it
- **A headless kernel no longer installs gist dependencies without being asked.** `install_deps()` prompts `[Y/n]` on the real terminal and treats a bare Enter as yes — correct at a terminal, and wrong everywhere else, because an auto-spawned kernel has stdin on `/dev/null` (systemd's `StandardInput=null`, or `Popen(stdin=DEVNULL)`) where `readline()` returns `""` immediately. The prompt therefore read as unattended consent, and headless is how every kernel spawned by the bridge now runs — so a boot could resolve and `uv pip install` whatever any reachable gist's `__repld_deps__` happened to name, with the question and the answer both going to the journal. `repld gist add` links gists from other projects by absolute path, so the declaring file need not be one in the project you opened. The gate is now a genuine tty check rather than a stream-exists check (`gates.tty_prompt` returns `None` when there is nobody to ask, which is what its docstring already claimed), and `install_deps` reports what is missing and installs nothing when it can't prompt, printing a copy-pasteable `uv pip install --target …` for the shared deps dir. At a real terminal nothing changes, bare Enter included. **If you only ever run headless kernels, gist deps now need one deliberate install** — start `repld` in a pane once to be prompted, or run the command it prints
- **Runtime state is no longer world-readable when `XDG_RUNTIME_DIR` is unset** — the case on macOS, in most containers, and in any env-scrubbed spawn. `Path.mkdir(mode=0o700)` applies the mode only to the directory it creates last, so the shared `/tmp/repld` root was coming out 0755, and task spill files (which hold whatever a cell printed — tokens, API responses, query results), browser screenshots (which can show authenticated page content), and the session registry (which names every project's cwd and socket) were being created 0644. The fallback root is now `/tmp/repld-{uid}`, created 0700 explicitly and refusing to run if another user owns it; spill files, screenshots written to the runtime dir, the event log, the session registry, and the lockfile are all created 0600 with no window at looser permissions. A screenshot written to a caller-supplied `path` still respects the caller's umask. Under a real `$XDG_RUNTIME_DIR` nothing was ever exposed — `/run/user/N` is itself 0700 — so this only changes behaviour on the fallback path. **If you run repld on a system without `XDG_RUNTIME_DIR`, stop any running kernel before upgrading:** its state lives under the old `/tmp/repld` path and the upgraded CLI will not find it (it stays running and will be replaced by a fresh kernel; the stale directory can be deleted)

### Fixed

- **A gist using `from __future__ import annotations` got a wrong tool schema.** Under PEP 563 every annotation reaches `inspect.signature` as a *string*, so `int` stopped mapping to `integer`, `float` to `number`, and an `Annotated[T, "..."]` wrapper was invisible — such a gist silently got every parameter typed `string`, no parameter descriptions, and an "unmapped type" warning per parameter. Schemas now resolve through `typing.get_type_hints(..., include_extras=True)`, falling back to the raw annotations if a forward reference can't be resolved. That import is common in real gists, so this was not hypothetical
- **Adopting a late-appearing venv sent a malformed channel push.** `push_kind(content, kind)` was called with its arguments swapped, so the notification's content was the bare word `venv` and its `kind` was a sentence containing a filesystem path. Both parameters are `str`, so it type-checked, linted and ran; the only path that reaches it needs a venv appearing mid-session, which no test covered. A `push_kind` arg-order sweep now runs in phase 4 across every call site in `src/`
- **Answering one gate could strand another.** The pane tracked a single open gate, while `gates` has always allowed several at once — and since `repld gate`, an answer can arrive out-of-band for any of them. Answering an older gate cleared the pane's slot, leaving the gate actually on screen unanswerable from stdin. The pane now tracks the full set, drops the one that was answered, and re-shows whatever is still waiting
- **`repld status` could warn about a virtualenv belonging to neither party.** `_print_python` asks `bind.project_venv()` about the *kernel's* project, but that function's `$VIRTUAL_ENV` fallback ignores the cwd it was given — so running `repld status` from an activated venv, against a kernel whose project has no `./.venv`, compared that kernel's Python to the shell's venv and reported "project packages are not importable" about something unrelated to it. `project_venv` grew an `ambient=False` for callers asking about another process's project
- **Gist dependencies could never be installed under a system Python.** `install_deps` still refused when `sys.prefix == sys.base_prefix`, printing `use: uv tool install repld-tool --with <pkg>` instead — a leftover from when deps went into the active venv. They go to the shared, interpreter-versioned directory via `uv pip install --target … --python sys.executable` now, which resolves with or without a venv in sight; `ensure_deps_on_path` dropped its twin gate when that changed and this one was missed. So a `pip install --user repld-tool` could never accept the prompt, and the advice it printed named the tool venv that the shared directory exists to replace
- **`repld restart` reported failure while a healthy kernel was coming up.** `spawn_headless` returned `False` for two unrelated outcomes — the spawn failed, and a racing boot already owns the systemd unit. The bridge polls either way and was fine; `repld restart` treated it as fatal and returned 1 without printing anything at all. It now returns `STARTED` / `INCUMBENT` / `FAILED`, so only the last is terminal, and the bridge says which of the other two happened rather than claiming to have spawned a kernel someone else started
- **`choose()` answered by number returned the number.** The prompt renders its options as `1=alpha, 2=beta`, so typing an index is the obvious thing to do — and the TUI's stdin reader passed the line through verbatim, so `choose("Pick", ["alpha", "beta"])` returned the string `"2"` rather than `"beta"`. Coercion now lives in one place (`gates.parse_response`), shared by the pane and `repld gate answer`, so an index resolves to the option and an out-of-range one is rejected instead of silently becoming a bogus answer
- **The loop watchdog reported a kill it hadn't performed.** After `REPLD_LOOP_KILL_THRESHOLD` it cancels the longest-running task via `loop.call_soon_threadsafe` — a callback on the very loop it just declared wedged, so it cannot run until that loop moves again. The channel push said `killed blocked task`, telling the agent a task was gone while it might keep running for minutes. It now reports the cancellation as requested, and says it takes effect when the loop unblocks. The escalation itself is unchanged
- **Dropped an atexit hook that could never do anything.** The browser disconnect registered at boot was guarded on `loop.is_running()`, but `_shutdown` stops the loop before atexit runs — so the guard fired on every path that reached it and the hook was dead. (The guard was right: without it, every browser-attached shutdown blocked a full 5 s on a coroutine nothing was left to drive.) No behaviour change — a pinned tab's pill removes itself, along with its `beforeunload` guard, once Python stops heartbeating, which is exactly what a stopped loop looks like from the page
- **One unreadable session file could take down `repld status` and `repld stop --all`.** `list_sessions()` deliberately falls back to the *filename* pid when a session file's contents don't parse, so a live kernel's file isn't deleted out from under it — but it then returned the unparseable payload anyway. Every consumer indexes `pid` directly (`repld status`, `repld stop --all`, the dashboard's session sidebar), so an entry that got there precisely *because* its pid didn't parse crashed the command with a `KeyError` or `TypeError` — and `repld status` is exactly what you reach for when something is already wrong. The liveness fallback is unchanged; only the unusable payload is now dropped, so the documented contract holds: every returned entry is a dict with a parseable `pid`
- **A long-lived kernel never reclaimed its screenshots or its oversized tool/resource responses.** Task spills have been aged out at `_EVICT_AGE` since they were introduced, but that sweep walks the *task registry*, and three producers write into the runtime directory without ever creating a task entry: `resources/read` responses over the preview budget, browser tool responses over it (`browser_tree` and `browser_network` routinely are), and every `browser_screenshot` PNG. The only other rule, the boot sweep, reclaims what a *dead* pid left behind — no help to a kernel that stays up for weeks, which is the whole design. So these accumulated for the life of the process, under `$XDG_RUNTIME_DIR` meaning RAM held until logout. They now age out by mtime at the same one-hour bound as a task spill, with live tasks' spill files excluded so the two rules can't race. The retention promise is unchanged and now uniform: a path handed to the agent in a tool response stays readable for about an hour
- **A hung dependency install could wedge the whole kernel.** `install_deps()` ran `uv pip install` / `pip install` with no timeout, and two of its three call sites are in the gist import hook — a gist edited or first imported mid-session re-scans its `__repld_deps__`, and that runs on the kernel's shared asyncio loop, inside the `exec` that triggered the import. A resolver stalling on an unreachable index therefore blocked every task, ticker, and channel push for as long as it hung, with the loop watchdog reporting a blocked loop it could not attribute to anything in user code. Installs are now capped at 10 minutes — generous, since a cold cache building a sdist like numpy or cryptography legitimately takes minutes — and a timeout prints the command to run by hand rather than failing silently
- **A dead-but-unreaped kernel counted as running.** `pid_alive()` asked `os.kill(pid, 0)`, which succeeds for a zombie — a process that has already exited and is only waiting for its parent to collect it. repld makes these routinely: the bridge never waits on the kernel it spawns, so a kernel that dies first sits unreaped until the bridge exits. Three things went wrong as a result: `repld stop` / `restart` reported "pid N did not exit within 10s" (and exited non-zero) about a process that had in fact exited, `read_lock` blessed a lockfile whose kernel was gone, and the new boot sweep declined to reclaim that kernel's spill files. `pid_alive()` now checks `/proc/<pid>/stat` for state `Z`; where there is no procfs it degrades to exactly its previous behaviour
- **`repld log` printed cell output one *chunk* per line instead of one line per line.** Cell output reaches the event log as a byte stream — a single `print("a", b)` in user code arrives as four separate chunks, and a chunk can be a bare newline — so `print()`-ing each record turned one line into four and put a blank line between every real one. Output is now written verbatim, the way the TUI always did it, with a pad so a record following output that didn't end in a newline still lands on its own line
- **A request could hang forever if the kernel died at exactly the wrong moment.** The bridge registers a request id before writing it, so a send that fails gets answered by the orphan sweep. But the socket can also go to `None` between the liveness probe and the write — the reader thread hitting EOF concurrently — and that path returned with the id already registered. Nothing would ever answer it: the client waited indefinitely, and `_drain_inflight` then burned its full 10 s timeout at session shutdown. It now goes through the same orphan path a failed send does, answering `-31001`
- **`repld gist lint`'s `deps` rule no longer flags optional imports.** It walked every import in the file, so the standard soft-dependency idiom — `try: import x / except ImportError: x = None` — was reported as an undeclared dependency, telling you to require something you had deliberately made optional. Imports inside a `try` whose handler catches `ImportError` (or `ModuleNotFoundError`, `Exception`, `BaseException`, or a bare `except:`) are now skipped. Only the `try` body counts: an import in the handler is the *fallback* and is still a hard requirement, as is one under a `try` that catches something unrelated
- **Gist dependencies now install somewhere durable, and stay visible to a bound kernel.** They previously went into whichever venv was active, gated on a `"uv/tools/" in sys.prefix` test. Both halves broke once the kernel began binding itself to the project: that test is false under a `uv run` overlay, so the accumulated `~/.local/share/repld/deps` became invisible to every bound kernel, and fresh installs landed *in* the overlay — a different temp directory on each invocation, so they vanished before the next boot and the install prompt returned forever. Installs now always use `uv pip install --target` into a shared directory keyed by interpreter version (`…/deps/py3.12`), which is put on `sys.path` under any prefix. It is **appended**, not prepended, so a gist declaring `httpx>=0.27` can't shadow the version the project resolved. This also settles a longer-standing annoyance: gist deps no longer live in the project venv, so `uv sync` can't prune them. **The loose files directly under `~/.local/share/repld/deps/` are now unused** — the versioned directories fill on demand, so expect one install prompt per project on the first boot *with a terminal* after upgrading (a headless kernel reports and skips — see the Security note above); the old contents can be deleted by hand
- **`repld exec` is no longer slowed by the venv bind** (~336 ms → ~82 ms). It resolves a lock path and talks IPC; user code runs in the kernel, which is already bound, so re-execing the CLI through `uv run` bought nothing. Only `repld`, `repld bridge`, and `repld restart` — the commands that become or spawn a kernel — bind now
- **A kernel that failed to start printed nothing at all.** `install_tee()` runs partway through boot, and `_Tee.write` deliberately never touches the underlying stream — the display thread owns the terminal — so anything failing after that point reached only the event log, with no display thread yet alive to render it. The result was a bare non-zero exit with an empty terminal, which is how an over-long `--socket` path, a permissions problem, or an already-bound port all presented. The boot sequence now writes `repld: kernel failed to start` plus the traceback to the real stderr before re-raising, so the event log still gets its copy through the normal unhandled-exception path
- **Private gists were skipped by dependency scanning and by `repld gist lint`, but only when local.** An underscore-prefixed file isn't a gist — it stays out of listings, MCP instructions, and tool discovery — but it *is* importable, and a public gist doing `from _helpers import x` relies on it. `_iter_gist_files()` filtered privates out of the installed-directory branch and, inconsistently, not out of the linked one, so the same file behaved differently depending on whether it was local or co-linked into another project (`gist add` follows sibling imports with no public/private check, so it will link one). Consequences: a private helper's `__repld_deps__` was never scanned at home, and the sibling importing it died on a bare `ModuleNotFoundError` with nothing pointing at the file that needed the package; `repld gist lint` never checked private files at all; and a co-linked private would have surfaced in the linking project's instructions as a gist. Dependency scanning and lint now see private files wherever they live, listings and tool discovery never do, and lint skips only the `firstline` rule on them — their docstring is never extracted, so there is nothing there to truncate. **A private gist that declares `__repld_deps__` is now scanned at boot — and prompts, on a kernel that has a terminal to prompt at — where previously it was skipped silently.**
- **`repld gist lint`'s `deps` rule flagged correctly-declared gists.** It compared each import's root against `__repld_deps__` verbatim, but a declaration is a *distribution* name and an import is a *module* name, and the two are unrelated for a lot of common packages — a gist declaring `pillow` and `resvg-py` was told it hadn't declared `PIL` or `resvg_py`. The runtime had already solved this (`gist_deps._distribution_import_names()`, which `_is_importable()` consults), so the linter and the installer disagreed about the same declaration. Declarations now resolve to the set of import roots they can satisfy: the name normalized, the installed distribution's real top-level modules, and a short static alias table for the packages that aren't installed where lint runs. Two more false positives went with it — the `"."` self-dep is resolved to the project's own package instead of skipped, and an underscore-prefixed file next to a gist counts as an importable sibling (`is_public_gist_file()` decides what gets *listed* as a gist, not what resolves on `sys.path`, so `from _helpers import x` was being reported as an undeclared dependency)
- **`repld gist lint`'s `shape` message described a stricter rule than it enforces.** The check is the presence of a `->` on the docstring's first line; the message asked for `-> {shape}`, so a legitimate `-> [DnsRecord(...)]` or `-> the new record's id` looked like it had been let through by accident. The message now says what the check actually wants — the looseness is deliberate and stays
- **`repld gist lint`'s `legacy` rule now catches both halves of the pre-0.1.0 tool convention.** It flagged `__repld_tools__` but not the `_tool_x(args: dict)` handler signature that used to pair with it — and a gist can hit the second without the first, by declaring tools the modern way while still taking a single dict. Nothing warned about those: `gists._warn_deprecated` only fires on the declaration list, so the handler stayed silent until someone actually called the tool. Both are removed in 0.3, and both now surface statically with a message naming the offending function
- **A running kernel now reclaims its own task spills.** The boot sweep below only collects what a *dead* pid left behind, so a live kernel's spill files — one per output-producing cell — accumulated for its entire life. That was invisible when a kernel lasted as long as its terminal; with headless kernels meant to run for weeks it is one tmpfs file per cell, held in RAM. The prune pass that already drops a completed task's registry entry an hour after it finishes now unlinks its spill file at the same time. That pass also gained a clock: it used to run only every 50th `finalize()` call, which never arrives on a kernel that executes a handful of cells and then sits idle — precisely the headless case — so the hour was a floor and not a bound. It is now driven by the loop watchdog's tick as well, which runs whether or not the kernel is doing anything. **The spill path in a `[full output: …]` marker is therefore good for roughly an hour after the cell completes**, not indefinitely; anything still wanted by then should be written somewhere durable. Resource and tool spills (`{pid}-{label}-…`) and browser screenshots have no owning task and are still collected only by the next boot's sweep
- **Per-process scratch left by dead kernels is now swept at boot.** Task spills, resource spills, and browser screenshots are written to the runtime dir by the process that produced them and were never collected — nothing runs on the way out of a SIGKILL, and no later kernel looked. On a busy machine that is thousands of files: under a real `$XDG_RUNTIME_DIR` they sit in tmpfs, i.e. RAM held until logout, and under the `/tmp/repld-{uid}` fallback they are permanent. Every such file is named `{pid}-…` so a booting kernel reclaims a dead pid's leftovers in one pass. A recycled pid only makes the sweep skip a file — a running kernel's own output can never be touched. Screenshots gained the `{pid}-` prefix to join the scheme; any written under the old name are left alone (harmless scratch, and tmpfs clears them at logout anyway)
- **`repld log` and the live TUI render the same events identically again.** Three formats had drifted apart since the log was added: the human-gate response was worded differently in each, `repld log` dropped the tab title from browser attach lines, and the plain-ANSI channel push left the colour switched on after the top border, tinting the pushed content cyan. The formats now come from one module
- A bridge whose first kernel spawn timed out (a cold project with many gists, or one installing `__repld_deps__`) replayed the client's `initialize` onto the kernel it then reached, emitting `tools/list_changed` before the client's own `initialize` response had been answered — plus a misleading "reconnected to a fresh kernel" on stderr. The handshake is now cached only once it is on its way to a kernel, so the first one is never mistaken for a replacement
- `repld help`'s state check stat'd `./.pyrepl.lock` and advised deleting a stale one by hand — a file that no longer exists, and advice the flock mutex made wrong anyway
- `repld stop --all` aborted the whole sweep with a `ValueError` if any session file lacked a `socket_path`, instead of skipping that one entry
- `repld exec`'s interactive banner listed every injected builtin except `no_display`, so the one builtin whose whole purpose is to be discovered at the REPL (call a function that already prints its own output, without printing it twice) was the one nobody was told about
- The dashboard hint file was only ever written by browser code, so on a kernel that never touched the browser it didn't exist. Two things silently didn't work as a result: `repld status` couldn't authenticate to the dashboard API and so never printed its `active: N task(s), M ticker(s)` line, and the dashboard drew a fresh random port on every restart instead of reclaiming its previous one. The hint is now written as soon as the server binds. It merges rather than replaces, and only rewrites the browser keys when a browser pool exists — otherwise a headless kernel's boot would discard the previous kernel's restorable Chrome session before it had a chance to offer it back

### Removed

- **`repld init` is gone, and repld no longer writes anything into a project.** Registration is now one command — `claude mcp add repld -- repld bridge` — recorded at the client's local scope. **Migration: run that once per project, then delete the project's `.mcp.json` and the `<!-- repld:start -->` block from its CLAUDE.md.** Both files were snapshots of scaffolding advice frozen at the moment `repld init` ran, and a stored copy of a command drifts from the command repld actually wants: the MCP entry did exactly that when `bind.rebind_exec` moved binding inside repld, leaving every earlier project on `uv run repld bridge` and paying a per-session `uv sync` to reach the same interpreter. The CLAUDE.md block was redundant on top of that — every claim in it (`@every`/`defer`/`notify`, browser auth, "suggest wiring it up", "run `repld help`") is already in the MCP `initialize` instructions, which are always loaded *and* always current, which is why the block needed a `--force` diff to update at all. Setup now lives in `repld help` and the README. A project's only repld-shaped files are the ones that are actually its own content: `repld_init.py` and `gists/`
- **`repld --init FILE` is gone, replaced by an auto-detected `repld_init.py`.** **Migration: `mv repl.py repld_init.py` and drop `--init` from any launch command** — the file is found by name now, and nothing needs passing. The flag only ever fired on one path: a human starting the kernel by hand *and* winning the flock. Since lazy spawn, the kernel that matters is usually one nobody started — the bridge spawns it on first tool use, `repld restart` respawns it, `repld_restart` replaces it — and `spawn._kernel_argv` carries `--no-display` and nothing else, with no init path in the lockfile for it to replay. So a project whose kernel *hosts* something (a server, a tunnel, a worker in `__main__`) lost its entire bootstrap the moment its hand-started kernel was replaced, silently. Passing `--init` to a kernel that stood down for an incumbent was equally quiet: it printed "nothing to do" and exited 0 without running the file. Both failure modes are gone rather than fixed, because there is no longer a per-invocation flag to drop
- **The `__repld_tools__` tool-registration list is gone.** A gist registers MCP tools with typed `_tool_*` functions and nothing else; the hand-written schema list that predates them is no longer read. A file still carrying one is now ignored rather than warned about, so `repld gist lint`'s `legacy` rule stays on as the only thing that reports it — reworded from "deprecated" to "removed", because the consequence changed from a warning to silence. **If you have a gist using it, migrate before upgrading:** give each argument its own typed parameter, move the tool description to the docstring's first line, and put per-parameter descriptions in `Annotated[T, "..."]`. Two things get better as a result. A tool taking a single `dict` argument now works — `_tool_submit(payload: dict)` used to be indistinguishable from the legacy `handler(args)` shape and was silently skipped, so the removal is what makes an object-valued argument expressible. And a file mixing both conventions no longer has its typed functions suppressed, since the precedence rule that let `__repld_tools__` win is gone with it. `resolve_tool` returns a plain callable instead of a `(handler, old_style)` pair, and `protocol._gist_tool` no longer branches on calling convention
- **`repld[browser]` now requires Chrome 140+.** `Tab.fetch()` carried a hand-chunked `btoa` fallback for browsers without `Uint8Array.prototype.toBase64` (needed because `String.fromCharCode` spread over a whole buffer blows the call stack past ~64K arguments). `toBase64` has been on by default since Chrome 140 and Baseline since September 2025, so the fallback is gone and the requirement is stated instead — in the README, `repld help browser`, and the phase-6 test notes. Only binary response bodies ever touched that path
- Dead compatibility branches: the dashboard hint file's "older kernels wrote a bare port int" migration (the hint moved to `$XDG_RUNTIME_DIR` this release, so a file that old can't be at the path we read), and `browser_dispatch._session_for`'s fallback for a plain `Browser` bound to `__main__.browser` (unreachable since `BrowserPool` became what the lazy builtin bootstraps)
- `repld init` no longer writes `.gitignore` entries, and no longer creates a `.gitignore` to hold them: nothing repld writes at runtime lands in the project directory any more. Existing `.pyrepl.*` lines in a project's `.gitignore` are harmless and can be deleted

## [0.1.1] - 2026-07-24

### Added

- `repld gist lint [name...]` — AST-based best-practices checker for gist files. Four rules: `firstline` (module docstring's first line must stand alone — it's what gets truncated into tool listings/instructions/resource descriptions), `shape` (public methods returning dict/list/Any should document the return shape on the docstring's first line), `deps` (non-stdlib imports should be declared in `__repld_deps__`), `legacy` (flags `__repld_tools__` statically instead of only warning reactively at tool-call time). Suppress a finding with `# gistlint: ignore=<rule>` on the flagged line or the line above. Scans the same dirs + precedence a live kernel resolves against (`~/.repld/gists`, `./gists`, and `.links`), not just the local project. Documented in `repld://docs/guide`'s Conventions section, `repld help gists`, and `repld help`'s command list
- `__repld_deps__` gained a `"path:some/dir"` form — prepends a local, non-pip-installable directory to `sys.path` (e.g. a vendored git submodule), relative to the gist's project root. No install step; a missing directory warns loudly with a `git submodule update --init` hint instead of a bare `ModuleNotFoundError` the first time the gist runs. `gist lint`'s `deps` rule treats top-level modules/packages found in the resolved directory as declared, so imports from it don't false-positive. Modules imported from a path dep get the same mtime-based auto-reload as gists — `_GistFinder` tracks them too, flagged separately so editing vendored code re-imports the new version without a kernel restart, but without triggering the gist-registry/API-summary side effects that don't apply to third-party code

### Changed

- `gists.import_hint()` is now a shared helper — `build_instructions()` (always-loaded MCP instructions) and `introspect()` (the on-demand `repld://gists/{name}` resource) both call it instead of each computing their own import line, so they can't show different (or no) import advice for the same gist
- `browser_screenshot` tool description now warns that reapplying `Emulation.setDeviceMetricsOverride` on an already-emulated tab can leave viewport metrics inconsistent — recommend a fresh tab per distinct size and verifying `clientWidth === innerWidth` before trusting the capture

### Fixed

- Console-error and dashboard-connect channel notifications built short target IDs (e.g. `9222:5CA9D0`) from the raw CDP `targetId` without lowercasing, unlike the canonical `make_target()` helper — an ID copied straight from a notification would fail every `browser_*` tool call, since `_is_target_id()`'s classifier regex only matched lowercase hex and silently misrouted the uppercase ID as a URL glob instead of a target ID (surfacing a confusing "no tab matching" error rather than something actionable). `_push_error_text` and the dashboard's connect summary now lowercase consistently with `make_target()`; `_is_target_id()`'s regex is case-insensitive and `_split_target()` normalizes its prefix, so any uppercase ID — from any source — now resolves instead of just being masked at the two known origins
- `install_deps()`'s tool-venv path (`uv pip install --target ~/.local/share/repld/deps`) resolved each newly-missing dep in isolation, blind to everything already installed in that shared, cross-project directory — two gists whose transitive deps disagreed (e.g. one pinning `pydantic==2.13.4`, needing `pydantic-core==2.46.4`, while a later install pulled a newer `pydantic-core` in unrelated to that constraint) could silently leave mutually-incompatible versions on disk. `gist_deps.py` now maintains a `.repld-manifest.txt` of every requirement ever installed there and re-resolves the full accumulated set on each install, not just the new arrivals
- `Tab._wait_for_node` cached the root `DOM.getDocument` nodeId once before its poll loop; a document replaced mid-wait (SPA navigation, HMR reload) left it stale, so `click()`/`type_text()`/`wait_for()` silently never matched and raised a misleading "Element not found" instead of surfacing the navigation race. Root nodeId is now re-fetched every poll iteration
- `gists.resolve_tool` could dispatch to a typed `_tool_*` function in a gist file that also declared unrelated legacy `__repld_tools__` entries — a case `scan_tools`/`tools/list` never advertised, since a legacy-declaring file suppresses all typed tools in that file. Both now share one `_declared_tools` classifier, so listing and dispatch agree
- `Tab._setup_binding` called `self._session.execute()` directly instead of `self._exec()`, skipping the session-gone recovery every other CDP call gets — pin setup could raise instead of self-healing across an HMR reload or navigation race
- `Tab.sse()` and `Tab.lifecycle()` ordered results by `ORDER BY rowid`, a column their underlying views never expose (only `id`) — both raised a DuckDB `BinderException` on every call
- Dashboard's per-pattern tab-count display recomputed glob matching in JS with a hand-rolled regex that always escaped `[`/`]`, diverging from the server's `fnmatch`-based watch matching — bracket-class patterns could show a stale count. Counts are now computed server-side in `BrowserPool.snapshot()` next to the actual match logic, and the client just renders them
- `gists._resolve_json_type` didn't unwrap parameterized generics (`list[str]`, `dict[str, int]`) when inferring an MCP tool schema from a `_tool_*` signature — fell through to the "unmapped type" warning and silently schema'd the param as `"string"`
- `gists.signature_for_path` (and `signature()`) picked a gist's *first* public class by file order for the "here's how to import this" hint, with no regard for whether it was the entry point — a custom exception type declared before the main class (a common pattern, e.g. `GigahostError(RuntimeError)` before `Gigahost`) would win instead, producing a hint that imported the wrong class. Now skips classes whose name or base ends in `Error`/`Exception`
- `gist_deps.scan_deps()` only ever ran once, at kernel boot — adding `__repld_deps__` entries to a gist file already imported by a long-running kernel never got checked or prompted again; you'd have to know to restart the whole kernel process to get the install prompt. `gists._check_reload()` now re-scans just the changed file's deps on every auto-reload, so a newly-declared dependency gets caught the next time the gist is (re-)imported instead of silently waiting for a restart. Also deduped `_GistImportHook`'s `base`/`top` reload checks (equal for any flat, non-package gist) so the new prompt can't double-fire for one reload
- `gist_deps.install_deps()` never pinned `--python` when installing into `_TOOL_DEPS_DIR` (the side-install dir used when repld runs as a global `uv tool install`, unlike the project-venv branch right below it, which already did). `uv pip install --target` with no `--python` resolves against uv's own default interpreter, which can silently differ from `sys.executable` — a binary wheel (`cffi`, `pydantic-core`, `rpds-py`, ...) built for the wrong Python ABI lands in the shared deps dir and fails with a bare `ModuleNotFoundError` for its compiled extension deep inside whatever imported it, nowhere near the actual cause. Now pins `--python sys.executable` in both branches
- A gist file created *after* the kernel had already booted skipped its `__repld_deps__` scan entirely on first import — `_GistImportHook`'s pre-import `_check_reload()` call is a no-op for a module `_GistFinder` has never resolved before (nothing in `_managed` to compare mtimes against yet), so only the boot-time scan (everything present at start) or a later edit (`_check_reload`'s own rescan) ever triggered it. "Write a new gist, `import` it right away" — an entirely normal same-session workflow — silently skipped the check, surfacing missing deps as a bare `ModuleNotFoundError` instead of an install prompt. `_GistFinder.find_spec` now runs the same scan the first time it tracks a `fullname`, across all three of its resolution tiers (local gist dirs, cross-project links, `path:` dep dirs)
- `gist_deps._is_importable()` only ever tried a dep's declared name verbatim (modulo `-`→`_`), so any package whose importable module name differs from its PyPI distribution name (`pyyaml`→`yaml`, `beautifulsoup4`→`bs4`, ...) was reported "missing" on *every* scan forever, install or not — the install itself succeeded harmlessly each time, but the kernel re-prompted on every boot and every first import indefinitely. Now falls back to `importlib.metadata.packages_distributions()`'s reverse mapping (distribution name → actual top-level import names) before giving up; the cache is dropped after `install_deps()` installs something so a same-session install is picked up immediately
- Kernel shutdown blocked up to 5 real seconds in `_browser_cleanup` whenever a browser had ever been attached: its atexit hook scheduled `real.disconnect()` on the kernel's asyncio loop via `run_coroutine_threadsafe`, but `_shutdown()` always stops that loop *before* atexit runs, so the coroutine had nothing left to drive it forward and the wait just ran out its 5s timeout every time. Because `_cleanup_lockfile`'s atexit hook (LIFO-ordered) runs *before* `_browser_cleanup`'s in practice, `.pyrepl.lock` was already deleted up to 5s before the process actually exited — a real window for a fresh `repld` invocation to start while the old kernel (and its IPC sessions) were still alive. `_browser_cleanup` now skips the coroutine dispatch entirely when the loop isn't running. Related: `ipc.Session._close_locked()` closed the raw socket but left its `rfile`/`wfile` `TextIOWrapper`s for GC/interpreter-shutdown finalization to close, which surfaced as an uncatchable `BrokenPipeError` ("Exception ignored in...") when their buffered flush hit the already-dead socket — both are now closed explicitly, with the same errors caught deliberately instead
- `Tab._reattach()` only recovers from CDP *session* invalidation (same target, new session — e.g. HMR reload); when a target is destroyed outright and replaced (a genuine cross-origin/site-isolation process swap), it still re-attaches by the old target id, so `Target.attachToTarget`'s raw CDP error ("No target with given id found") propagated straight out of `_exec()` uncaught, unexplained. Now catches that failure and raises a clear error pointing at `browser_tabs` to find the replacement, instead of passing Chrome's raw text through unchanged
- `repld/__init__.py`'s `TYPE_CHECKING` block stubbed `notify`/`defer`/`every`/etc. for `import repld; repld.notify(...)` gist patterns but never added `browser`, despite `kernel.py` genuinely injecting it into the module at runtime — every gist referencing `repld.browser` type-checked as an attribute-access error

- Gist AST parsing is memoized on file mtime — a single MCP `initialize` previously re-parsed every gist file four times (docstring scan, signature, usage, tools)
- `repld exec` consumes every `--socket` flag occurrence (first value wins) instead of only stripping the first `--socket PATH` pair
- Gist registry writes are skipped after the first import of a given gist per kernel process (previously a full read-parse-write of the registry JSON on every re-import)
- Importing `repld.display` no longer asserts on `sys.__stdout__`/`sys.__stdin__` at import time, so `--no-display` works in stdio-less environments; display mode checks at startup instead
- `browser_screenshot`'s resize step now uses Pillow instead of a hand-rolled PNG decoder (new `pillow` dependency in the `browser` extra) — handles every PNG variant Chrome can emit and runs in a thread executor instead of blocking the kernel's shared asyncio loop for the ~150-200ms a resize takes on realistic screenshot sizes
- `repld gist new` template scaffolds the new typed `_tool_*` pattern (no `__repld_tools__`)
- `__repld_tools__` still works as a legacy override for custom schemas, but prints a one-time-per-gist deprecation warning at boot
- Kernel boot no longer silently reconnects Chrome ports and re-watches tab patterns from the previous session's dashboard hint — it now prompts on the terminal (`[Y/n]`, default yes) before restoring. Headless boot (`--no-display`) or non-tty stdin skips the restore entirely rather than blocking on a prompt no one can answer
- Browser tab pin state (`_pinned`, `_pin_reason`, `_pin_origin`, `_heartbeat_task`) now lives on `CDPSession` instead of `Tab` — `Tab` wrappers are recreated on every `get()`/`_iter_tabs()` call, so pin state used to reset whenever a tab was re-fetched. `CDPSession` persists for the life of the attachment, matching the existing pattern for `capture_bodies`
- `Tab.fetch()` / `browser_fetch`: string request bodies now default to `Content-Type: application/x-www-form-urlencoded` (dict bodies unchanged, still `application/json`); caller `headers` override, matched case-insensitively
- `BrowserPool.get()`'s cross-browser retry loop caught bare `RuntimeError`, which could mask a real CDP/ready-signal/reattach failure as "try the next browser" instead of surfacing it. A dedicated `TabNotFoundError` now carries the "no such tab" case specifically, and the retry only catches that
- Several rounds of internal cleanup from codebase health passes: kernel boot split into phase helpers; duplicated ready-signal polling, `__repld_usage__` extraction, AST/warn-once parsing (`__repld_tools__`/`__repld_deps__`), target-ID parsing, tool-venv `sys.path` setup, attach+enable_fetch+wrap, `push_channel` call sites, dashboard `_bound_port`, terminal-bypass writes, heartbeat constants, `INSERT INTO` event-store statements, and doc-resource lookups each consolidated into one helper/constant; `tasks.snapshot()`/`kernel.preview_since()`/`gists._read_registry()` added as proper public seams instead of reaching into another module's private state; `_gate()` gained per-kind overloads instead of a `type: ignore`; assorted doc drift fixed (`browser.patterns()` being a property, `browser_key`'s description, selector/deps docs, GUIDE's builtins recap documented as the sanctioned doc-overlap exception)

### Fixed

- Cross-process JSON files (lockfile, dashboard hint, session registry entries, gist registry, link manifest) were written with plain `write_text`, so a crash mid-write could leave a truncated file for concurrent readers (the bridge and `repld exec` read the lockfile/hint on every connect). All five now go through one tmp-then-`os.replace` helper; the dashboard hint's `0600` mode also lands before the file becomes visible instead of just after
- Dev-checkout kernels prepended the tool-venv gist-deps dir (`~/.local/share/repld/deps`) to `sys.path`, shadowing the project venv's site-packages with extension modules built for a different interpreter — a stale Pillow there silently disabled the `browser` builtin at boot. The dir is now only added when actually running from the uv tool venv, matching `install_deps`'s gating
- `browser.connect()` with no port ignored `REPLD_CHROME_PORT` and always defaulted to 9222; it now honors the env var like the rest of the browser layer
- The per-tab DuckDB event store was read (`tab.network()`/`console()`/`body()` MCP tools) from IPC reader threads while the kernel loop wrote events through the same connection object — DuckDB connections aren't thread-safe. Reads and `clear()` now run on a per-call cursor (duplicated connection, DuckDB's sanctioned cross-thread pattern)
- `get_task` with an unknown `task_id` returned a *successful* response whose `_meta` carried only `{task_id, error}` — no `done`/`text` fields — instead of a JSON-RPC error like `cancel` does for bad input
- `repld help browser` listed `tab.controls()` and `tab.invoke()` under the sync DuckDB-query heading; both are async (calling them bare returns a coroutine). The browser guide's `controls()` entry also didn't say it's async
- `tab.capture_bodies` / `tab.label` setters fell back to the deprecated `asyncio.get_event_loop()` when the session had no loop — now raise a clear `RuntimeError` instead (the fallback was unreachable in practice; the loop is always set at attach)
- `__repld_deps__` requirements with extras (e.g. `httpx[http2]>=0.27`) were falsely flagged as missing on every boot — the parsed package name kept the `[...]` suffix, which `importlib.util.find_spec` can never resolve
- Cell execution counter (`_N`/`_` history) could race and hand out duplicate numbers when two MCP sessions called `exec` concurrently, since the increment wasn't atomic across IPC reader threads
- `repld gist add <name>` failed for gists that are only ever invoked as MCP tools (never `import`ed by user code) — they were never written to the cross-project gist registry
- `browser_screenshot` silently returned the untouched, full-size PNG (with no error) for any screenshot that wasn't 8-bit RGB/RGBA — while still reporting the *intended* downscaled dimensions in the response metadata, so callers had no way to tell the image didn't actually match what was reported
- `Tab.sse()` / `Tab.lifecycle()` queried with `LIMIT 500` but no `ORDER BY`, while their backing views (`sse_entries`, `lifecycle_entries`) are defined oldest-first. Once a session passed 500 SSE messages or lifecycle events, these methods silently returned the *oldest* entries instead of the most recent — the opposite of every sibling query method (`network()`, `console()`)
- Browser doc drift: the `repld help browser` topic documented `tab.type_text(..., enter=)` (the real parameter is `press_enter=`) and neither it nor `docs/browser` listed `tab.key()`; the `confirm()`/`choose()` type stubs were missing the `tab=` parameter that routes gates to a pinned tab's pill UI
- `BrowserSession.connect()` fetched `/json/version` with a synchronous `urllib.request.urlopen(timeout=5)` on the kernel's shared asyncio loop — every connect *and* auto-reconnect could stall the whole kernel for up to 5s when Chrome was slow or unreachable. Now runs in a thread via `asyncio.to_thread`
- `tab.body()` / `row.body()` called from `exec` code (which runs *on* the kernel loop) deadlocked for 10s and then errored whenever the body wasn't in the capture store — the sync CDP fallback blocked the very loop it needed to run its coroutine on. Now fails fast with guidance to use `await tab.cdp('Network.getResponseBody', ...)` instead; the thread-side (MCP tool) path is unchanged
- `browser_screenshot` wrote the PNG to disk synchronously on the kernel loop; the write now runs in a thread executor like the resize step
- Tab label state (`tab.label`) lived on the ephemeral `Tab` wrapper, so re-labelling a re-fetched tab orphaned the previous label's injected script and DOM bar instead of replacing it. Label state now lives on `CDPSession`, matching pin state
- Re-attach with a CSS `ready=` selector always timed out: the ready poll held a `DOM.getDocument` nodeId from before the page settled, which goes stale when the document is replaced mid-load and then silently never matches. The poll now evaluates `document.querySelector(...)` via `Runtime.evaluate`
- `_parse_pkg_name` split multi-clause requirements (`foo>=1.0,!=1.2`) at whichever version specifier set iteration found first, sometimes producing a mangled package name and a spurious install prompt. Now splits at the earliest-occurring specifier
- Channel-kinds doc in `repld help exec` was missing `pin_lost` and `browser_disconnect`
- A gist declaring a dep whose dotted parent package is missing (e.g. `__repld_deps__ = ["ruamel.yaml"]`) crashed kernel boot — `importlib.util.find_spec` raises `ModuleNotFoundError` for such names instead of returning `None`; now treated as "not importable"
- `resources/read` truncated every resource to the 4KB exec-output preview, so `repld://docs/*` never returned the actual docs to MCP clients (only a head/tail preview plus a local spill path). Resources now return full text up to 64KB — only the unbounded browser network/console dumps can still spill — and honor each resource's declared mimeType (`repld://browser/controls` was declared `application/json` but always served `text/plain`)
- The dashboard's per-tab Detach button never worked: `BrowserPool.snapshot()` built target IDs without lowercasing while the detach lookup compares lowercased, so every click returned "Target not found"
- HMR/navigation re-attach built a brand-new CDP session, silently discarding the tab's event history, body-capture state, and pin/label state, and leaking the old session's DuckDB connection. Re-attach now preserves the session in place (same mechanism as Chrome-restart reconnect) and re-registers the label script
- `tap`/`swipe` and `browser_tree` bypassed the session-gone recovery wrapper, so touch input and tree reads failed permanently after an HMR reload while clicks recovered
- Every browser mutation tool polled a heavyweight DuckDB HAR view at 20Hz *synchronously on the kernel loop* while waiting for network idle; settle now reads an in-memory in-flight counter maintained on the event path
- `repld gist new -h` / `add -h` / `rm -h` treated `-h` as a gist name (or exited non-zero); they now print usage and exit 0
- Scaffolded gists (`repld gist new`) shipped an unused `import os` that lint flags in the user's project
- Doc drift: `repld help browser` claimed CSS selectors use `DOM.getBoxModel` (the code uses `DOM.getContentQuads`) and understated `ready=` as CSS-only (it also accepts JS expressions)
- Missing `task_id` on `get_task`/`cancel` returned a generic internal error (`-32603 KeyError`) instead of the proper invalid-params error (`-32602`)
- Multi-line `str` cell results print verbatim instead of being `repr()`-escaped into an unreadable single line with literal `\n`s
- `repld://gists/{name}` signature listings no longer render `@property`/`@cached_property` methods with call parens (was misleading agents into calling e.g. `.pid()` and getting a `TypeError`)
- `browser_fetch` / `Tab.fetch()` silently sent string bodies with no `Content-Type`, so the browser defaulted to `text/plain` and form-decoding servers saw an empty form — root cause was in `Tab.fetch()`'s header defaulting, not the MCP transport
- `browser_fetch` tool schema: `body` had no declared `type`, so MCP clients could silently flatten a dict argument to a JSON string instead of sending it as an object. Now typed `["object", "string"]`, matching what the handler actually accepts
- `no_display(value)` only unwrapped on a cell's bare last expression — direct assignment (`x = await foo()`) left `x` bound to the internal wrapper object instead of the real value, contradicting its own "still returning it... for programmatic use" contract. `compile_cell()` now also collects top-level simple-assignment targets (`x = ...`, chained `x = y = ...`, annotated `x: T = ...`) and `run_cell()` unwraps `_NoDisplay` off them after they're bound. Doesn't cover tuple/list/starred/attribute/subscript targets or walrus expressions nested in larger expressions
- `browser.watch(pattern)` silently reported "Attached 0 new tab(s)" when a matching target existed but the CDP `Target.attachToTarget` call failed (e.g. another debugger already attached to it) — the exception was swallowed and logged only at `DEBUG` (no logging is configured anywhere in the package, so it was never actually emitted). The returned summary now appends `N attach attempt(s) failed: <target>: <reason>` when any attach errors, instead of looking identical to "nothing matched the pattern"
- `BrowserJSError.stack` was always a copy of `.text` (never an actual stack trace), contradicting the docs' claim of a "preserved stack trace". Now parses CDP `exceptionDetails.stackTrace.callFrames` into a real multi-frame string
- Kernel boot swallowed dashboard-start, Chrome-port-reconnect, and pattern-re-watch failures with a bare `except: pass` — a broken dashboard import or failed session restore was invisible. Now logged to stderr
- `repld exec` had no `--socket` flag despite `repld bridge` supporting one, so pointing `exec` at a kernel on a non-default socket path required setting `REPLD_SOCKET` instead
- `Tab._wait_ready()` silently no-op'd on navigate/reload whenever `ready=` wasn't explicitly passed (the common case) — `self._ready` was `None` so the method returned immediately, skipping even the default `document.readyState === 'complete'` wait. Now falls back to that expression instead of returning early
- `Browser.detach(pattern=...)` (and detach-all) never unpinned tabs before detaching, unlike `detach_target()` — a pinned tab's pill, beforeunload guard, and heartbeat task leaked whenever it was detached via a pattern or `detach()` with no argument
- `resolve_gate()` could raise (or silently do nothing, depending on timing) when the terminal and a pinned tab's pill raced to resolve the same human-gate — `Future.set_result()` on an already-resolved future raises `InvalidStateError`, which wasn't caught. First responder now always wins cleanly
- Gist registry writes (`_register()`) crashed on a corrupt `gist-registry.json` instead of resetting it, unlike the read path (`registry()`); both now handle corruption the same way
- `_every_registry` (the set of active `@every` tickers) was mutated from the asyncio loop thread, sync-cell threads, and the dashboard's HTTP thread with no lock — the same missing-lock bug class as the task registry, just not yet hit in practice
- `_tasks` (the task registry) had no lock guarding it against concurrent watchdog-thread/IPC-reader-thread access; entries were also never evicted after completion, leaking forever in a long-running kernel. Now locked and evicted 1h after `done_event`
- `BrowserPool.get(target, timeout=N)` gave each connected Chrome instance the *full* timeout before trying the next one, so with N connected browsers a "not found" could take up to N×timeout instead of timeout total. Now shares one deadline across all browsers
- `Tab.capture_bodies` setter flipped the visible flag before `enable_fetch()`/`disable_fetch()` had actually finished (or even started, since the CDP call is fire-and-forget from a sync setter) — code reading `capture_bodies` right after setting it could see the new value while Fetch interception was still in its old state
- `_pick_victim` (the loop-watchdog's kill-candidate scan) iterated `tasks._tasks.values()` directly instead of a snapshot, risking a `RuntimeError: dictionary changed size during iteration` if a task was added or finalized mid-scan
- `hint_for_name()` (the "did you mean to import this gist?" suggestion) only scanned `_installed_dirs`, so it never suggested a gist that was only present via cross-project linking (`repld gist add`)
- `observe.py`'s iframe-tree attachment matched on a substring of the accessible name, so any node whose name happened to contain "Iframe" could be misattached as a child iframe's tree root
- `gists.install()` didn't update the existing `_GistFinder`'s directory list on repeat calls (e.g. after `repld gist add`), leaving the finder stale while `_installed_dirs` (and therefore `_find_gist`/`_iter_gist_files`) had already moved on
- `Tab.cdp()` (the raw-CDP passthrough MCP tool) called the session directly instead of going through `_exec`, so it — unlike every other `Tab` method — couldn't recover from a stale session after an HMR reattach
- `resolve_tool()` let a broken gist's import error escape `tools/call` instead of failing soft with a warning, the way `scan_tools()` already does for `tools/list`
- `_Tee.write`'s lazy spill-file open had no lock, so two threads sharing a `task_id` (a sync cell's `asyncio.to_thread` worker racing the loop thread) could both open the spill file, leaking the first handle and losing its output; `Tab.pin()` checked-then-set `_pinned` across two `await`s, so a concurrent `pin()` call could pass the guard twice and leak a heartbeat task that later reset `_pinned=False` out from under the real one; `CDPSession.enable_fetch()`/`disable_fetch()` had the same check-await-set gap
- `browser.get(<target-id>)` raised `TabNotFoundError` when another `attach()` was already in flight for that exact target, instead of retrying like the glob-based lookup does — extracted the shared poll interval into `_ATTACH_POLL_INTERVAL_S`
- `Browser.detach_target()` let unpin/detach exceptions propagate while `detach()` swallowed them — same operation, inconsistent error handling; both now go through one `_unpin_and_detach()` helper
- `Tab.fetch()` / `browser_fetch` always read the response as `r.text()`, so binary payloads (ZIP, PDF, image, protobuf) came back as mangled mojibake instead of the actual bytes. Now reads `arrayBuffer()` and probes UTF-8 validity via `TextDecoder(..., {fatal: true})` — text responses are unchanged (JSON still auto-parsed), invalid UTF-8 is base64-encoded (native `Uint8Array.prototype.toBase64()` when available, chunked `btoa` fallback otherwise) and returned as `base64Encoded: true`, matching the `{body, base64Encoded}` shape `tab.body()` already uses
- `gists.py`'s tool-schema builder silently mapped any unrecognized parameter type (e.g. `bytes`, `Path`, `Optional[str]`) to JSON Schema `"string"` with no warning, unlike every other malformed-input path in the file; `gist_deps.py`'s `__repld_deps__` scanner had the same silent-fallback gap for non-list values
